# 本体场景验收

本目录验证第 6 步：手写用户原话与模型工具提议经过真实协调者、子 Agent、Skill、网关、业务后端和 LangGraph 检查点完成办理。只替换模型输出，不替换业务工具、确认规则或核验代码；禁止构造真实模型客户端。

## 场景与预期

| 场景 | 用户轮数 | 核对的业务结果与边界 |
| --- | --- | --- |
| 跨单取消与退货 | 3 | 两种能力分别准备；多项收到“好的”不提交，“全部确认”后取消办公椅订单、登记水管退货；退款只发生一次 |
| 同单地址与两件商品变更 | 3 | 先确认新地址，再把灯泡和键盘的规格一起修改；同类诉求合并，同单动作依次确认；补付差价 16.52 元 |
| 换货成功、备用退货撤销 | 2 | 换货核验通过后撤销条件退货，登记 24.71 元换货差价；不产生退货操作 |
| 无库存、改办条件退货 | 2 | 先真实查询规格库存，再解除退货条件；仍须展示并取得下一轮确认才登记退货 |
| 改口取消另一张订单 | 3 | 旧准备项拒绝、原订单保留；任务修订后重新准备和展示，下一轮确认才取消新目标 |
| 补充缺少的取消原因 | 3 | 信息不完整时无准备操作；补全后准备并展示，再确认退款 |
| 跨会话继续 | 3 | 关闭业务库、档案和检查点后重新打开；先重新验身份，立即“确认”不能授权旧展示；再次展示后才可确认 |

七个场景共 19 条用户消息、8 段聊天。每项独立初始化数据库；跨聊天的单项场景共用原库和检查点。最终比较完整业务快照，覆盖无关订单、用户和商品未变；任务完成必须有真实核验结果。假模型脚本必须恰好执行完，不能把预算或模型失败后的兜底回复当作正常成功。

## 开发数据与配置

来源为 [固定中文数据清单](../../data/README.md) 中的业务数据库和政策。夹具抽取合成用户 `junjie_liu_6635` 的四张订单及所需商品，保留原始金额、规格、库存和订单字段；使用真实政策与项目 Skill。选择只基于业务记录，不使用官方题目的原话、参考动作或判分答案，也不修改源文件。

这些脚本是开发验收用例，不能作为冻结困难评测集或真实模型任务成功率。真实模型的理解、规划与自然语言断言能力将在评测接入后验证。

使用根目录 `config.toml` 的默认参数：子 Agent 12 步、每轮协调 8 次、上下文 64000 字符、近期 4 轮。场景没有另设更大的预算。模型只引用代码产生的任务标识；`condition` 由脚本化协调模型解释，测试不会直接修改任务状态。

## 运行与查看

在项目根目录运行：

```bash
uv run pytest -q tests/acceptance
```

需要保留本次验收产物时，新建独立目录：

```bash
mkdir -p runs
acceptance_run=$(mktemp -d runs/acceptance-XXXXXX)
uv run pytest -q tests/acceptance --basetemp "$acceptance_run/cases" --junitxml "$acceptance_run/junit.xml"
```

JUnit 记录实际通过或失败，不由场景助手自行宣布通过。`cases/` 下每项包含：

- `dialogue.json`：默认运行参数、已验证会话、逐轮用户原话、实际回复、展示与任务结果；仅供观察，不参与恢复。
- `business.sqlite`、`checkpoints.sqlite`、`archive.sqlite`：原业务库、唯一任务检查点和完整对话档案。
- `traces/`、`models/`、`usage.jsonl`：完整 span 树、每次模型调用原文与费用账本。

夹具会逐项核对 span 开始与结束、并发父子范围、会话与轮次、模型文件和账本一一对应。每次提交都必须关联同会话上一轮的实际展示、本轮真实原话及确认、正确任务修订，以及提交后读取业务库的核验。

用 `uv run ttwill trace <场景目录>/traces/chat1.jsonl` 查看树状轨迹；续办场景另有第二段聊天文件。
