# 实施计划

> 最近更新：2026-11-13
>
> 原则：**先做出完整的项目本体（D 组架构），能实际对话办理业务；再接入评测**，包括 τ²-bench 适配、A / B / C 三组基线、开发任务转换和正式实验。
>
> 每一步都应能独立运行、有测试，再进入下一步。细节以 `docs/` 中的设计文档为准。

## 第一部分：项目本体

| 步骤 | 完成的部分 | 跑通的标志 |
| --- | --- | --- |
| 0. 仓库初始化 | git、uv、目录结构、`.env.example`、测试框架 | 空项目能安装依赖、运行测试 |
| 1. 基础设施 | 统一 LLM 调用层（含假模型）、轨迹（span 树、JSONL 落盘、命令行查看） | 用假模型发一次调用，能在轨迹中看到完整记录 |
| 2. 业务后端 | SQLite 业务库（导入 τ² 中文包已编译的中文数据库）、订单与售后操作、两阶段写入（准备 / 提交）、身份归属校验；Agent 层工具定义与工具网关；业务库快照导出为 τ² 格式；参考动作重放的语义一致性校验（不需要模型）；命令行对话入口 | 能在命令行里查询订单；写操作必须先准备、再提交；官方题的参考动作在两边执行后数据库哈希一致 |
| 3. 子 Agent | 能力注册表、子 Agent 工具循环、结构化返回；政策按章节拆为 Skill，`load_skill` 按需加载，加载前关联写工具被拒绝；订单服务与售后两种能力 | 单独派给子 Agent 一个任务，能加载对应 Skill、执行并返回结构化结果 |
| 4. 协调者与护栏 | 身份验证、任务状态、按任务分派（可并行，同一订单的写任务串行）、确认判定（规则 + LLM 判定）与代码提交、执行后核验、协调者循环的未完成检查 | 一句话含两件事能分派给不同子 Agent 并都办完；写操作必须经用户确认后由代码提交 |
| 5. 可恢复运行时与上下文 | 基于 LangGraph 检查点的暂停 / 恢复（等待确认、跨会话继续）；对话档案与任务状态持久化；协调者上下文编译（分级压缩：工具结果引用化 → 超预算时摘要） | 中途退出后重新进入，能从上次的任务状态继续办理；超长对话能触发压缩且仍能正确办理 |
| 6. 本体验收 | 用一组手写对话脚本走通典型场景：复合诉求、条件依赖、改口、信息缺失、跨会话继续 | 场景都能走通，轨迹完整可查 |

**业务后端的做法**：自己实现，不调用 τ² 的工具代码。直接导入 τ² 中文包已编译的中文数据库，MVP 的操作语义与 τ² retail 政策保持一致。这个后端就是自建购物平台的起点，之后在其上扩展。

**一致性校验放在第 2 步**：第 3～6 步都建立在这个后端上，语义偏差越早发现越好。校验只需要安装 τ² 和读取官方题的参考动作，不调用模型。

## 第二部分：接入评测

| 步骤 | 完成的部分 | 跑通的标志 |
| --- | --- | --- |
| 7. τ² 评测适配 | 把本体包装成 τ² Agent（`HalfDuplexAgent`），接官方用户模拟器；自写评测入口，用第 2 步的快照替换预测侧数据库判分 | D 组用真实模型跑通 1 道 τ² 题并得到判分 |
| 8. 基线实现 | A 组（单 Agent 工具循环）、C 组（单 Agent + 任务状态，复用本体的护栏）、B 组（EchoMind 意图路由移植）；A / B 组使用开放“提交”工具的写操作包装，确认只靠政策约束 | 四组都能在同一道题上运行 |
| 9. 开发任务转换 | 用官方映射表把 64 道题转为中文版，并用 `retail_50` 校验转换脚本 | 校验通过；四组能在开发集上批量运行 |
| 10. 正式评测 | 困难任务集、正式评测、实验报告 | 另行设计 |

## MVP 之后

实时网页演示；在业务后端上扩展为完整的自建购物平台；第二阶段导购。
