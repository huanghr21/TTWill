# 实施计划

> 最近更新：2026-11-14
>
> 原则：**先做出完整的项目本体（D 组架构），能实际对话办理业务；再接入评测运行器**，包括 τ²-bench 适配、A / B / C 三组基线、开发任务转换和正式实验。困难评测集的设计与冻结提前完成，不等到正式评测时才开始。
>
> 每一步都应能独立运行、有测试，再进入下一步。细节以 `docs/` 中的设计文档为准。

目录按 [02 Agent架构设计.md](<02 Agent架构设计.md#项目目录结构>) 逐步引入；本轮已确定的约定及其主文档位置见 [08 决策记录.md](<08 决策记录.md>)。目录方案不代表以下步骤已经实施。

## 第一部分：项目本体

| 步骤 | 完成的部分 | 跑通的标志 |
| --- | --- | --- |
| 0. 仓库初始化 | git、uv、目录结构、`.env.example`、测试框架 | 空项目能安装依赖、运行测试 |
| 1. 基础设施 | 统一 LLM 调用层（含假模型）、轨迹（span 树、JSONL 落盘、命令行查看） | 用假模型发一次调用，能在轨迹中看到完整记录 |
| 2. 业务后端 | SQLite 业务库（导入 τ² 中文包已编译的中文数据库）、订单与售后操作、两阶段写入（准备 / 提交）、身份归属校验；Agent 层工具定义与工具网关；业务库快照导出为 τ² 格式；`retail_50` 中文参考动作重放；命令行业务入口 | 能在命令行里查询订单；写操作必须先准备、再提交；`retail_50` 参考动作在两边执行后数据库哈希一致，7 个写工具未覆盖的部分有无模型单元测试 |
| 3. 子 Agent | 能力注册表、带步数上限的工具循环、代码组装的结构化返回；Skill 按实例加载、加载前关联写工具被拒绝；政策协议条款排除清单；订单服务与售后两种能力 | 单独派给子 Agent 一个任务，能加载对应 Skill 并返回结果；`actions` 及执行结果来自网关记录，实例之间不共享 Skill 解锁记录 |
| 4. 协调者与护栏 | 身份验证、任务状态、订单写任务按“订单 × 动作类型”汇总分派；同单写任务串行、不同动作逐个确认；确认判定与代码提交、执行后核验；每轮分派轮数上限和未完成检查 | 多诉求能汇总、分派并办完；写操作只接受最近一次回复所展示操作的确认，写任务仅由核验代码标为 `done`；两种循环超限均能明确失败并记录原因 |
| 5. 可恢复运行时与上下文 | LangGraph 检查点是任务状态的唯一持久化来源；对话档案存取；暂停 / 恢复；跨会话恢复重新验身份、按后端操作记录对账；上下文编译（工具结果引用化 → 超预算时摘要） | 中断后同一任务继续使用原业务库；已提交但检查点未更新的操作能恢复为已提交，不重复提交，核验通过后才标为 `done`；跨会话的待确认操作重新展示；长对话压缩后仍能办理 |
| 6. 本体验收 | 用开发种子中的手写对话脚本走通典型场景：复合诉求、条件依赖、改口、信息缺失、跨会话继续 | 场景都能走通，轨迹完整可查 |

**业务后端的做法**：自己实现，不调用 τ² 的工具代码。直接导入 τ² 中文包已编译的中文数据库，MVP 的操作语义与 τ² retail 政策保持一致。这个后端就是自建购物平台的起点，之后在其上扩展。

**一致性校验放在第 2 步**：第 3～6 步都建立在这个后端上，语义偏差越早发现越好。先用已有官方中文版参考动作的 `retail_50` 重放校验；7 个写工具中未覆盖的部分补无模型单元测试。第 9 步完成其余 64 道题转换后，再将重放校验扩展到这些题。此校验不调用模型。

**第 2、5 步的断点验收**：第 2 步按任务 ID、修订号与动作类型确定性生成请求关联标识，验证同一请求重复准备不生成第二个操作，任务请求内容修改并递增修订号后使用新标识。第 5 步分别在“准备成功但操作 ID 未写入检查点”和“提交成功但检查点未更新”处中断，验证从恢复的任务状态重算相同标识，能找回或清理操作、正确恢复订单占用、不重复写入；不为每次准备额外拆图节点或强制保存检查点。恢复的待确认操作仍需重新展示，已提交操作仍需核验后才能标为完成。

**第 3～4 步的职责边界**：模型对任务状态和结构化返回只提出任务增、改、撤，以及 `missing` 和 `message_hint`；`condition` 保留自然语言，由协调者判断。代码从网关记录填入操作及执行结果，写任务的 `done` 只能由核验代码设置。派出实例时由代码构造“会话身份 + 能力 + 实例 ID”的调用上下文，Skill 加载记录随实例销毁。子 Agent 工具步数与每轮分派轮数分别设上限，数值放入配置；超限将相关任务标为 `failed` 并写入 guard span，由协调者说明原因或转人工。详细确认有效期、同单动作次序与状态边界见 [02 Agent架构设计.md](<02 Agent架构设计.md>)。

同一订单的同类商品在准备前汇总成完整清单；同单写任务的串行锁覆盖“准备 → 提交或被拒绝”，动作先后顺序写入 Skill，并由后端提交时复核。

第 4 步同时验收两类边界：多个待确认操作收到范围不明的“好的”时继续追问，不自动全部提交；换货成功等条件已确定后，不再需要的备用任务由协调者提出撤销，代码记录原因并作为终止状态，不计为失败。

**评测数据隔离从第 2 步就按任务设计**：每个评测任务的每次重复运行使用独立业务库；同一跨会话任务的多段聊天共用该库和任务检查点。第 5 步恢复时以业务后端的操作记录为权威对账，不在检查点之外另存任务状态副本。

**困难评测集在调优前冻结**：本体实现可用假模型测试和开发种子验证；在针对 D 组进行任务表现调优前，先确定并冻结困难评测题、分层、预期结果与判分口径。之后只用开发题调优，冻结题留作评测，不能先用评测题调好 D 组再冻结。冻结与评测运行器接入是两件事，不受下表步骤 7～10 的先后顺序限制。

## 第二部分：接入评测

| 步骤 | 完成的部分 | 跑通的标志 |
| --- | --- | --- |
| 7. τ² 评测适配 | 把本体包装成 τ² Agent（`HalfDuplexAgent`），接官方用户模拟器；自写评测入口，用第 2 步的快照替换预测侧数据库判分 | D 组用真实模型跑通 1 道 τ² 题并得到判分 |
| 8. 基线实现 | A 组（单 Agent 工具循环）、C 组（单 Agent + 任务状态，复用本体的护栏）、B 组（EchoMind 意图路由移植）；A / B 组使用开放“提交”工具的写操作包装，确认只靠政策约束 | 四组都能在同一道题上运行 |
| 9. 开发任务转换 | 用官方映射表把 64 道题转为中文版，用 `retail_50` 校验转换脚本，并将第 2 步的语义一致性校验扩展到这 64 道题 | 转换与参考动作重放校验通过；四组能在开发集上批量运行 |
| 10. 正式评测 | 运行 `retail_50` 与已冻结的困难评测集，补齐计划样本，分别报告终态一致率与含自然语言断言的任务成功率，整理失败分析和实验报告 | 按 [03 实验设计.md](<03 实验设计.md>) 完成可复现对照；未补齐样本时报告完成率和已完成样本上的成功率 |
