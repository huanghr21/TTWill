**业务后端的做法**：自己实现，不调用 τ² 的工具代码。直接导入 τ² 中文包已编译的中文数据库，MVP 的操作语义与 τ² retail 政策保持一致。这个后端就是自建购物平台的起点，之后在其上扩展。

**一致性校验放在第 2 步**：第 3～6 步都建立在这个后端上，语义偏差越早发现越好。先用已有官方中文版参考动作的 `retail_50` 重放校验；7 个写工具中未覆盖的部分补无模型单元测试。第 9 步完成其余 64 道题转换后，再将重放校验扩展到这些题。此校验不调用模型。

**第 2、5 步的断点验收**：第 2 步按任务 ID、修订号与动作类型确定性生成请求关联标识，验证同一请求重复准备不生成第二个操作，任务请求内容修改并递增修订号后使用新标识。第 5 步分别在“准备成功但操作 ID 未写入检查点”和“提交成功但检查点未更新”处中断，验证从恢复的任务状态重算相同标识，能找回或清理操作、正确恢复订单占用、不重复写入；不为每次准备额外拆图节点或强制保存检查点。恢复的待确认操作仍需重新展示，已提交操作仍需核验后才能标为完成。

**第 3～4 步的职责边界**：模型对任务状态和结构化返回只提出任务增、改、撤，以及 `missing`、子 Agent 备注 `note` 和协调者回复正文（原 `message_hint`，F3 拆分改名）；`condition` 保留自然语言，由协调者判断。代码从网关记录填入操作及执行结果，写任务的 `done` 只能由核验代码设置。派出实例时由代码构造“会话身份 + 能力 + 实例 ID”的调用上下文，Skill 加载记录随实例销毁。子 Agent 工具步数与每轮分派轮数分别设上限，数值放入配置；超限将相关任务标为 `failed` 并写入 guard span，由协调者说明原因或转人工。详细确认有效期、同单动作次序与状态边界见 [02 Agent架构设计.md](<02 Agent架构设计.md>)。

同一订单的同类商品在准备前汇总成完整清单；同单写任务的串行锁覆盖“准备 → 提交或被拒绝”，动作先后顺序写入 Skill，并由后端提交时复核。

第 4 步同时验收两类边界：多个待确认操作收到范围不明的“好的”时继续追问，不自动全部提交；换货成功等条件已确定后，不再需要的备用任务由协调者提出撤销，代码记录原因并作为终止状态，不计为失败。

**评测数据隔离从第 2 步就按任务设计**：每个评测任务的每次重复运行使用独立业务库；同一跨会话任务的多段聊天共用该库和任务检查点。第 5 步恢复时以业务后端的操作记录为权威对账，不在检查点之外另存任务状态副本。

**困难评测集在调优前冻结**：本体实现可用假模型测试和开发种子验证；在针对 D 组进行任务表现调优前，先确定并冻结困难评测题、分层、预期结果与判分口径。之后只用开发题调优，冻结题留作评测，不能先用评测题调好 D 组再冻结。冻结与评测运行器接入是两件事，不受下表步骤 7～10 的先后顺序限制。
