# 调研：τ²-bench retail 环境

> 调研日期：2026-11-12　｜　对象：[sierra-research/tau2-bench](https://github.com/sierra-research/tau2-bench) 2.0.0（2026-10-19），对照原版 tau-bench
>
> 方法：只读源码与数据文件，未安装或运行仓库代码。**[实]** = 读文件核实，**[推]** = 推断。

## 结论

**适合作为 MVP（订单服务 + 退换货）的数据来源、语义参照和评测基准。** 项目据此决定自建业务后端，以 τ² 中文数据库为初始数据（见 [02 Agent架构设计.md](<02 Agent架构设计.md#工具与业务后端>)）。

需要我们自己补的部分，恰好是本项目的特色：

| 缺口 | 影响 | 对策 |
| --- | --- | --- |
| 无商品描述、无浏览/收藏等行为数据 | 无法直接支撑导购与画像 | 第二阶段另找商品数据或自建 |
| 政策明文禁止“主观推荐” | 与导购冲突 | 第二阶段另写导购政策 |
| 退换货提交即生效 | 无完整售后生命周期 | 第三阶段扩展 |
| 无多会话、中断场景 | 无法直接测跨会话继续 | 借 `initial_state.message_history` 构造 |
| 任务少（114 题，test 仅 40） | 统计波动大 | 多次运行 + 自建困难任务 |

在批量修改商品的最后写入循环中复用了前一循环最后一次的 `variant`。
报告原样保留两题的不一致，所有其他终态字段均一致；没有修补上游或调整判分。
**已确认将这两题列为已知上游差异**，不影响第 2 步验收，详见 [05 实施进度](<05 实施计划.md#实施进度>)。

同一源码审查还发现三个政策与实现差异，本次 50 题参考动作没有触发：修改商品后的
`pending (item modified)` 仍被上游按 `pending` 接受；更换支付方式后取消订单时，
取消逻辑也对已有退款记录再次生成退款；换货允许换成原规格。
本体按本文政策校验这些情况，分别禁止继续修改、仅退净实付、要求不同规格，
并有无模型规则测试。第 9 步扩充参考题时需继续报告这类差异。

## 政策要点 [实]

| 规则 | 内容 |
| --- | --- |
| 身份验证 | 必须先通过邮箱或姓名+邮编定位用户；一次对话只服务一个用户 |
| 执行前确认 | 任何写操作前列出细节，得到用户明确的 “yes” |
| 单步执行 | 一次只调用一个工具；调用工具时不能同时回复用户 |
| 状态约束 | 取消、修改仅限 pending；退换货仅限 delivered；换货只能换同一商品的其他规格 |
| 只能一次 | 修改商品、换货每单只能调用一次；修改商品后订单不能再改或取消 |
| 退款 | 退回原支付方式或已有礼品卡 |
| 禁止 | 编造信息、给出主观推荐 |
| 转人工 | 仅限超出能力范围的请求 |

已知问题 [实]：工具层不强制身份验证，完全依赖模型遵守（任务 5 登记的 open issue）。

## 任务与判分 [实]

| 项 | 内容 |
| --- | --- |
| 数量 | 114 题；train 74 / test 40；2.0 官方基准使用冻结的 50 题子集 `retail_50` |
| 任务格式 | 用户场景（来电原因、已知/未知信息、行为指令、部分有人设）+ 参考动作序列 + 判分依据 |
| 参考轨迹长度 | 平均约 4.8 步，最长 13 步 |
| 判分 | 在新环境中重放参考动作得到目标数据库，与 Agent 运行后的数据库**做哈希比对**；路径不同但终态一致即通过。部分任务另有 LLM 判定的自然语言断言。各项相乘，任一项不过即为 0 |
| pass^k | 每题运行 n 次、成功 c 次，pass^k = C(c,k)/C(n,k)，再对任务取平均；表示 “k 次运行全部成功” 的概率，衡量稳定性 |

## 接入方式 [实]

- **自定义 Agent**：继承 `HalfDuplexAgent`，实现 `get_init_state()` 与 `generate_next_message()`，通过工厂函数注册；
- **用户模拟器**：LLM 扮演用户，通过 LiteLLM 调用，可接任意模型服务；
- **判分**：`evaluator_env.py` 构造预测侧（重放轨迹中的工具调用）与参考侧（执行参考动作）两个环境，比较数据库哈希。本项目替换预测侧，见 [02 Agent架构设计.md](<02 Agent架构设计.md#接入-τ²-bench-评测>)；
- **自定义任务**：写 JSON（用户场景 + 参考动作 + 判分依据），不需要写判分代码；
- **跨会话**：没有原生支持；`initial_state` 可预置历史消息和初始化动作。

## 第 7 步接入记录

2026-11-17，接入代码针对固定提交 `c06b07dd7c4d4ec61ba6ff9bcdf0b15dd7ef36d4`，没有改动上游。官方 wheel 不含默认数据目录，因此从同一提交补入 `zh/pack.yaml`，校验后直接构造官方文字人设；不依赖缺失的全套 τ² 数据目录。具体来源见 [data/README](../data/README.md)。

预测侧环境由本体完整快照构造，参考侧执行官方参考工具；自然语言断言继承官方 `calculate_reward` 聚合。固定版本没有给这个聚合入口提供模型参数，因此在本地子类中以相同提示词和 JSON 字段调用官方 `generate`，只绑定显式模型与参数，不修改官方全局常量。离线测试将提示词与上游逐字比较，并比较数据库结果与判分聚合。

**保留的官方限制**：该版本对缺失的 `results` 使用空列表，聚合使用 `all()`；因此空结果可能判为通过，部分结果也不会逐项核对是否覆盖全部断言。本步为保持判分兼容没有另加规则，测试记录这一行为；真实运行需保留判分原文。切换判分模型也影响与官方榜单的可比性，模型身份和参数必须在报告中披露。

当前 `retail_50` 的 `initial_state` 全为空，入口明确拒绝非空值。官方 `SimulationRun.agent_cost` 看不到本体内部调用，不能用于本项目成本统计；使用关联了所有角色和尝试的 `usage.jsonl`。

**动作诊断限制**：官方 `ActionEvaluator` 从对话消息的 `tool_calls` 匹配动作，而本体适配器只向调度器返回可见文本，内部网关调用保存在本体轨迹。因此报告中的 `action_checks` 不能用于判断本体是否调用过相应工具，也不能计算动作覆盖率；当前支持的判分依据不含 `ACTION`，这些诊断项不参与数据库与自然语言断言的最终聚合。业务结果以实际数据库终态为准，动作过程需读取本体网关轨迹。

2026-11-17 首次真实单题运行使用官方 `deepseek-flash`、`reasoning_effort=high`，题目 `6_zh_identity`、`seed=0`、`repeat=1`。报告位于 `runs/step7-deepseek-task6-20261117-attempt-001/report.json`：评测完成，用户主动终止，数据库不匹配、任务失败、奖励 0。参考侧执行无错误；本体库没有变化，目标单仍为 `delivered`，参考终态为 `exchange requested`。本体调用记录中的身份查询与订单读取成功，不应因 `action_checks` 全为 false 而否认这些真实查询。

此次 53 次 API 调用全部成功返回；输入 258260、输出 33126、缓存输入 169088 token，费用未配置单价而保留 `null`。官方 `simulation.json` 中的 `user_cost=0.0` 不能解释为免费；费用以统一账本为准，判分以 `report.json` 为准。

失败发生在协调工具协议与任务推进阶段：18 次直接文本回复、2 次同时调用三个工具触发格式护栏，3 次达到协调轮数上限、5 次上下文预算不足；对应请求确实传入了工具 schema。内部失败原因直接出现在用户回复中，用户最终退出。这属于已完成判分的业务失败。本题的 `nl_assertions` 为空，没有发生真实自然语言判分调用；离线验证与这一单题结果不能替代含断言任务的真实验收，也不构成正式成功率结果。

## 成本估算 [推]

官方文档中成本一节仍为 TODO。一次正式评测（`retail_50` × 4 次 = 200 段对话），按排行榜每条轨迹 $0.07～0.39 估算 Agent 侧约 $15～80；DeepSeek 预计低一个数量级以上，以首轮实际统计为准。

## 风险

1. **版本漂移**：锁定版本并写进报告；
2. **用户模拟器噪声**：多次运行、固定模拟器模型，失败分析时区分 Agent 错误与模拟器错误；
3. **题目本身的问题**：部分题目有已登记的问题；
4. **扩展即不可比**：改动数据或工具后只能自己和自己比。
