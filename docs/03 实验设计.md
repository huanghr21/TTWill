## 主实验：2×2 对照

### 研究问题

> 面对复合诉求、信息缺失和用户中途改口：**多 Agent 协作**和**显式任务状态 + 代码护栏**分别能带来多少可靠性提升？代价是多少？

### 对照组

把“是否多 Agent”和“是否有任务状态”两个因素拆开：

| | 没有任务状态 | 有任务状态 + 护栏 |
| --- | --- | --- |
| **单 Agent** | **A**：单 Agent 工具循环（接近 τ²-bench 官方基线） | **C**：单 Agent + 任务状态 |
| **多 Agent** | **B**：意图路由多 Agent（EchoMind 原架构） | **D**：任务驱动多 Agent（**本项目主方案**） |

| 组 | 说明 |
| --- | --- |
| A | LLM 读取系统提示和政策，自由调用工具，计划只存在于对话历史中 |
| B | 三路意图融合 → 一主一辅通用角色 → Composer 合成。从 EchoMind 轻量移植决策逻辑，去掉基础设施，换上同一套业务工具 |
| C | 单个 Agent 维护显式任务状态，受代码护栏约束 |
| D | 协调者维护任务状态并按任务分派预设能力（订单服务、售后），子 Agent 返回结构化结果，受同一套代码护栏约束。设计见 [02 Agent架构设计.md](<02 Agent架构设计.md>) |

**比较能回答的问题**（B 与 D 的协调方式不同，D vs B 是新旧设计的整体对比，不做交互效应分析）：

| 比较 | 回答的问题 |
| --- | --- |
| C vs A | 任务状态 + 护栏在单 Agent 下的收益 |
| D vs B | 新设计相对旧设计（EchoMind 意图路由）的整体收益 |
| B vs A | 意图路由多 Agent 是否有用（为删除旧架构提供依据） |
| D vs C | 任务驱动的多 Agent 是否有用 |

### 任务状态与护栏

**不是硬编码流程**：先办哪个、追问什么仍由 LLM 决定；任务状态把计划写到对话之外，代码护栏保证写操作安全。可以理解为：LLM 是司机，任务状态是行程单，代码约束是护栏。细节见 [02 Agent架构设计.md](<02 Agent架构设计.md#协调者与任务状态>)。

**工具与护栏在各组中的分布**：

| 约束 | 范围 |
| --- | --- |
| 后端约束：两阶段写入接口、身份归属校验 | 四组都有（平台行为） |
| Skill 门控：对应 Skill 加载前，关联写工具被拒绝调用 | 四组都有（政策提供方式的一部分） |
| Agent 层护栏：确认判定、执行后核验、协调者循环、同订单串行 | 只在 C / D 组 |

| | A / B | C / D |
| --- | --- | --- |
| 写操作 | 准备后由模型自己调用提交工具，确认只靠政策约束 | 没有提交工具，由护栏代码依据用户原话的判定结果提交 |

因此 A 组与 τ² 官方基线有两处不同，报告中需注明：官方写工具一步生效，而 A 组是准备后再提交；官方政策整份放在提示词里，而 A 组按 Skill 目录加载。C vs A 比较的正是“提交由谁授权”：代码依据用户原话，还是模型自觉。

τ² 政策本身就要求写操作前确认，A / B 组也会被要求遵守。排行榜上强模型的 pass^4 只有 40%～60%，说明“偶尔不遵守”真实存在。

### 组件消融（在 D 组内）

| 变体 | 去掉的组件 | 检验的问题 |
| --- | --- | --- |
| D − 确认 | 代码层的确认判定：改为与 A / B 相同，由模型自己调用提交工具（提交工具由协调者持有），只保留政策中的文字要求 | 误操作减少是否来自代码确认 |
| D − 核验 | 执行后核验 | 结果核验对完成率的贡献 |
| D − 结构化返回 | 子 Agent 返回自然语言，由协调者转述 | 结构化交接是否减少事实错误 |
| D − Skill 按需加载（可选） | 整份政策常驻提示词，不拆 Skill | 按需加载对成功率与上下文用量的影响；MVP 政策短，预期差异小 |

至少做一项，视时间与成本决定。

### 测试集

| 部分 | 来源 | 作用 |
| --- | --- | --- |
| 官方任务 | τ²-bench 2.0.0 中文包：`retail_50`（官方中文版）用于正式评测；其余 64 题自行转换为中文版，用于开发 | 检验基本能力；两者使用同一份中文数据库 |
| 困难任务 | 自建（复合诉求、条件依赖、改口、信息缺失、跨会话） | 体现本项目的研究重点 |

困难任务的类型与构造方式见 [01 阶段规划与MVP.md](<01 阶段规划与MVP.md#测试集扩充计划>)。结果**分开报告**：官方任务与困难任务各自的指标都列出，避免混在一起掩盖差异。

### 指标

| 指标 | 含义 | 判定方式 |
| --- | --- | --- |
| 任务成功率 | 数据库最终状态与预期一致 | 程序比对 |
| pass^k | 同一任务连续运行 k 次全部成功的比例，衡量稳定性 | 程序统计 |
| 误写操作数 | 执行了不该执行的写操作（含改口后的过期操作） | 程序比对 |
| 遗漏子任务数 | 复合诉求中未办理的部分 | 程序比对 |
| 不当追问 / 猜测 | 该追问未追问，或不需要追问却反复追问 | 轨迹分析（可辅以 LLM 评审） |
| 成本 | token 数、工具调用次数、对话轮数、耗时 | 程序统计 |

### 变量控制

- 四组使用**同一个 LLM、同一个业务后端、同一份工具定义、同一份政策、同一批任务**；写操作由谁授权提交是实验变量；
- 政策都以 Skill 按需加载提供（B 组移植时也用这一机制），整份常驻只作为可选消融；
- 模拟用户使用固定模型与固定设置；
- 每个任务重复运行 k 次（k 视成本确定），报告均值与波动；
- 固定 τ²-bench 版本，记录在结果中；
- 开发阶段在 64 道开发题（或其分层子集）上每题跑 1 次；正式结果在 `retail_50` 与困难任务集上跑 k 次（初定 k=4，与排行榜一致）；
- 开发中允许查看 `retail_50` 的失败案例，报告中如实说明。

### 模型与成本

默认全部使用 DeepSeek V4.1 Flash：Agent（各组相同）、用户模拟器、自然语言断言判分（需确认能否替换官方默认的 gpt-5.4-mini）。强模型（Claude / GPT）只在强弱分层实验或抽查判分一致性时引入。

Agent 与用户模拟器同一模型可能产生“同源偏差”，不影响组间相对比较，报告绝对分数时需说明。

一次正式评测约 200 段对话（50 题 × 4 次），另加困难任务；四组约 4 倍，消融另计。

### 预期与可能的结论

- 预期 C > A、D > B，且在困难任务上差距更大；
- MVP 中 D 相对 C 的优势可能很小，甚至因成本更高而不划算，预期在第二阶段出现跨场景任务后才明显；
- 若 B 不如 A，说明通用角色路由在业务办理中有害，作为删除依据；
- 任何结果都如实报告：收益出现在哪类任务上、来自哪个因素、代价是多少。

## 画像消融（第二阶段）

| 组 | 说明 |
| --- | --- |
| 无画像 | 只使用当前对话中的需求 |
| 仅历史画像 | 使用画像，但不吸收本次会话的反馈 |
| 画像 + 会话反馈 | 结合画像与本次对话中的反馈持续调整 |

需要专门构造的情况：**画像与当前需求冲突**（例如平时买游戏耳机，这次给父亲送礼），检验系统是否会被旧偏好干扰。

关注指标：约束满足率、推荐相关性、澄清轮数、事实准确性，以及最终下单成功率。

注意：模拟数据只能支持受控对比，**不能据此宣称真实用户点击率或成交率提升**。

具体设计在第二阶段开始前确定，画像结构见 [04 用户画像约定.md](<04 用户画像约定.md>)。
