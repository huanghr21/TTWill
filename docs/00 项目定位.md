## 为什么要重构

EchoMind 有一套可复用的工程底座：工具调用循环、RAG、MCP、会话记忆、请求幂等与副作用保护、调用轨迹、评测框架。但它的问题不是某一处不足，而是**各模块都“有了”，却都停在演示深度，彼此之间也没有围绕一个真实目标协同**。逐项打补丁（见 [项目优化清单](../../项目优化清单.md) 01～06 项）会被现有结构束缚，因此选择围绕新业务场景整体重构。

### 问题总览

| 模块 | 现状 | 问题 | 对应优化项 |
| --- | --- | --- | --- |
| 业务能力 | 错误码工具返回静态解释，账单工具只做字段检查和金额计算 | 没有连接任何业务数据，只能“给建议”，无法“办成事” | 06 |
| Agent 编排 | 三路意图融合输出单一意图 → 选主辅 Agent → 一次并行执行 → 合成回复；Agent 内部工具循环最多 3 次模型调用 | 没有任务清单，多诉求会被压成一个意图；外层不检查是否办完，没有补做、追问后继续的闭环 | 05 |
| 意图识别 | LLM / Embedding / 关键词三路，按固定权重（0.7 / 0.2 / 0.1）投票；Embedding 失败时回退到本地字符 n-gram；规则在识别和编排两处各扫一遍 | 复杂度高、收益未经验证；权重是拍定的；回退路径让“看起来在跑”与“真的有效”难以区分 | 05 |
| RAG | 演示知识库仅 2 个文件（约 4.6 KB）；按句号切块、500 字符硬切、无重叠；纯向量召回，无 BM25 / 混合检索；LLM 重排只看每个候选前 200 字符 | **检索面太薄**：数据量不足以暴露问题，也不足以证明改进；分块、召回、重排都没有专门的检索评测 | 02 |
| 记忆 | Redis 工作记忆 24 小时过期，15 条消息触发压缩；情景记忆只存摘要，原文截断到 500 字符；画像是 LLM 生成的自由文本 | 没有完整对话归档，中断后无法可靠恢复；画像不可用于检索与解释 | 04 |
| Skill | 按本轮消息的关键词子串命中后，把正文整段拼进 system | 换种说法就匹配不到；无法按需加载，占用上下文 | 01 |
| 多实例 / 多模型 | 实例池已预留，但每个角色只有一个实例；实例评分只看完成率和延迟 | 调度能力只存在于结构上，没有真实场景检验；评分与回答质量无关 | 03 |
| 评测 | 检查意图、角色、工具、实体是否命中，加 LLM 打分 | 只能说明“走对了路径”，不能证明业务结果正确；没有可复现的对照实验 | 贯穿各项 |

### 工程性被削弱的根源：缺少真实目标下的取舍依据

上面很多问题来自同一个原因：**没有一个可度量的业务目标，所以设计取舍没有依据，只能靠“多加一层保险”**。表现为：

- **防御性堆叠**：三路融合、多级回退、预留的多实例池……每一层都“可能有用”，但从未被证明有用，反而增加了理解和维护成本；
- **硬编码参数**：融合权重、3 次调用上限、500 字符分块、15 条压缩阈值等，都是拍定值，没有经过实验调整；
- **能跑不等于有效**：回退机制保证系统总能给出回复，却掩盖了上游失败（例如 Embedding 请求失败后静默走 n-gram）；
- **数据太少**：知识库、测试用例都只有演示规模，无法暴露真实问题，也无法用数据证明任何改进。

### 重构目标

TTWill 用一个真实业务场景（电商客服）作为**统一的度量目标**，让每个模块的保留、替换和删除都有依据：

1. **能力**：让系统**查到真实状态 → 执行业务操作 → 核验结果**，从“给建议”变为“办成事”；
2. **编排**：用显式任务状态支撑多诉求、改口与中断后继续，取代“单意图 + 一次分派”；
3. **检索**：以商品和政策为对象重建检索链路（结构化过滤 + 混合召回 + 排序），并配套检索评测；
4. **记忆**：完整归档 + 任务状态持久化 + 结构化画像；
5. **评测**：以业务最终状态为准，用对照实验证明改动的收益；
6. **做减法**：没有收益的复杂度（如三路意图融合）经实验验证后删除，删除本身也是有依据的设计取舍。

优化清单中的 01～06 项不再逐项实施，而是作为重构时的检查清单：每一项要么在新架构中解决，要么说明为什么不再需要。

## 业务范围

### 三个场景

| 场景 | 用户要做的事 | 系统需要的能力 |
| --- | --- | --- |
| 导购 | 找到合适的商品并下单 | 澄清需求、检索与比较商品、结合画像推荐、核验价格库存、创建订单 |
| 订单服务 | 了解或修改已有订单 | 查询订单、解释状态，在业务规则允许时修改或取消 |
| 退换货 | 退货、换货并跟进进度 | 判断是否符合条件、补齐信息、提交申请、查询进度、中断后继续办理 |

三个场景共用商品、库存、订单和政策数据，串成一条完整链路：

> 导购 → 下单 → 订单服务 → 退换货

### 跨场景请求

真实用户的一句话常常跨越多个场景，例如：

> 把上次买的耳机换成更轻的型号，没有合适的就退货。

这句话需要定位原订单、检索替代商品、判断换货条件，失败时转为退货。**这类关联任务是编排、记忆和评测的重点对象。**

### 退换货目标流程

最终希望覆盖完整的模拟流程：

> 提交申请 → 审核 → 寄回商品 → 确认收货 → 退款或补发 → 完成

审核、收货、到账等事件由模拟平台产生；Agent 负责办理、解释进度、处理异常，并依据业务记录核验结果。这是**最终目标**，按阶段逐步实现，见 [01 阶段规划与MVP.md](<01 阶段规划与MVP.md>)。

### 暂不纳入

| 方向 | 说明 |
| --- | --- |
| 商家侧 | 两个候选：① 商家处理买家售后；② 入驻、上架、申诉等平台商家支持。买家侧完成后再评估 |
| 跨境购物 | 涉及地区政策、费用和履约差异，资料与规则成本高 |
| 广告 | 涉及竞价与投放机制，与本项目目标关系较远 |
| 复杂促销、会员体系 | 暂不考虑 |

## 已确定的关键决策

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | 以买家侧客服为主，场景为导购 + 订单服务 + 退换货 | 共用一套业务数据，能形成跨场景任务 |
| 2 | 多品类，不限定单一品类 | 符合真实电商；首批数据可控制规模 |
| 3 | 导购后支持创建订单 | 让推荐结果真正进入后续业务，链路完整 |
| 4 | 业务数据和状态变更必须真实保存、可查询；支付、物流可模拟 | 评测以业务最终状态为准 |
| 5 | 导购采用“结合画像与业务约束的检索增强”路线 | 复用 EchoMind 的 RAG；保留后续引入推荐模型的空间 |
| 6 | 用户当前明确表达的需求优先于历史画像 | 避免旧偏好干扰新需求（如给家人送礼） |
| 7 | 画像使用结构化记录，由 Agent 补充 | 便于召回、过滤和解释，也便于做对照实验 |
| 8 | 整体范围先确定，开发按功能逐项实现、逐项验证 | 控制风险，每一步都可用 |
| 9 | 先做订单服务 + 退换货（MVP），再做导购 + 画像 | 前者最能补 EchoMind 短板，结果可程序化评测 |
| 10 | MVP 基于 τ²-bench retail 自建简易平台，功能扩展再考虑完整平台 | 已调研确认可用 |
| 11 | 保留并改造多 Agent：预设能力 + 动态编排（参照 Claude Code 子 Agent 机制），子 Agent 返回结构化结果 | 改造重点是协调方式；为导购、商家侧等扩展留出空间 |
| 12 | 架构按产品需求设计，τ²-bench 通过适配层接入 | 不让评测环境的限制影响核心设计 |

## 导购技术路线（第二阶段）

导购沿用 RAG 思路，但检索对象从文档变为**带结构的商品**：

> 理解需求与画像 → 检索商品 → 约束过滤与个性化排序 → 核验价格库存 → 生成推荐与比较 → 根据反馈调整

| 信息 | 处理方式 |
| --- | --- |
| 商品介绍、适用场景、使用说明 | 关键词 + 向量混合检索 |
| 品类、规格、尺寸、兼容性 | 结构化查询与条件过滤 |
| 价格、库存 | 以业务系统为准，下单时再次校验 |
| 退换货政策、常见问题 | 文档检索，保留适用范围与依据 |

关键设计点：

- **画像要影响“选出哪些商品”**，参与查询构造和候选排序，而不只是影响最后怎么介绍；
- 推荐理由必须依据实际检索到的商品与证据生成；
- Agent 负责追问、选择工具、根据反馈重新检索，并衔接下单与售后。

具体召回方法、排序规则，以及是否训练专门的推荐模型，在第二阶段设计时确定。画像约定见 [04 用户画像约定.md](<04 用户画像约定.md>)。

### 对“沿用 RAG 思路”的评估

**结论：方向成立，业界也常见，但要准确表述为“LLM 驱动的对话式检索推荐”，而不是“把推荐当成 RAG”。** 两者共享“召回 → 排序 → 基于结果生成”的骨架，但有四处本质差异，决定了哪些可以照搬、哪些必须另做：

| 差异 | 知识问答 RAG | 导购推荐 | 对设计的影响 |
| --- | --- | --- | --- |
| 什么是“好结果” | 与问题语义相关的证据 | 满足硬条件、适合这个用户的商品 | 语义相似 ≠ 适合购买；需要约束过滤和个性化排序 |
| 数据形态 | 非结构化文本 | 以结构化属性为主（价格、规格、库存），辅以描述文本 | 价格、尺寸等数值条件靠向量检索不可靠，应由 LLM 把需求解析为结构化过滤条件 |
| 是否因人而异 | 同一问题答案相同 | 同一需求，不同用户结果不同 | 排序阶段要引入画像特征，不能只靠 LLM 重排 |
| 如何评测 | 证据召回率、回答是否有依据 | 约束满足率、排序质量（需要“用户真实偏好”作为标准答案） | 需要带隐藏偏好的模拟用户或有交互记录的数据集 |

**可以直接复用的**：混合检索、查询改写、重排框架、基于证据生成推荐理由、工具调用循环。

**需要另做的**：

- **查询理解**：自然语言 → 结构化过滤条件 + 文本检索词（类似 self-query 检索）；
- **个性化排序**：画像匹配作为排序特征；LLM 重排只用于少量候选的精排或解释，避免成本高、结果不稳定；
- **推荐评测**：约束满足率、排序指标、多轮反馈后的收敛速度。

**商品库规模是前提**：只有几百个商品时，全量过滤就够了，召回阶段形同虚设，也就无从比较召回方案。商品库需要足够大、足够多样，检索与排序的实验才有意义。这同时能补上 EchoMind “检索面太薄”的问题：商品目录是一个有规模、可评测的检索语料。

**候选数据来源（待调研）**：Amazon Reviews 2023（多品类商品元数据、评论和用户交互）可同时提供商品库与用户历史行为；同一团队的 Amazon-C4 提供带上下文的复杂商品查询，可作为导购测试集参考。两者的规模、许可证和适用性需在第二阶段前核实。

**面试表述**：讲清楚“哪里像 RAG、哪里不是”，比直接说“推荐就是 RAG”更能体现理解深度。
