## 统一 LLM 调用层

所有模型调用（Agent、确认判定、摘要，以及我们自己发起的模拟用户与判分）都经过一层薄封装：统一接口；代码里只写模型档位（如 `flash` / `strong`），映射放在配置里；每次调用记录 token、费用、延迟并写入轨迹；统一处理重试与超时；提供假模型供测试使用。

**例外：τ² 内部的调用。** τ² 自带的用户模拟器和判分组件在 τ² 内部通过 LiteLLM（一个统一调用各家模型的开源库，τ² 的依赖）发起请求，不经过我们的调用层。不修改 τ² 的代码，而是通过 LiteLLM 的回调（callback）把这些调用的 token 与费用记入同一个费用账本。

## 轨迹

### 用途

| 用途 | 说明 |
| --- | --- |
| 调试与失败分析 | 区分是协调者拆错任务、子 Agent 执行错，还是护栏误拦 |
| 实验指标 | 误写操作、遗漏子任务、成本等指标从轨迹统计 |
| 演示 | 实时网页的链路面板直接消费轨迹事件 |
| 回放 | 用记录的模型输出离线重放，不再调用模型 |

### 数据模型：span 树

参照 OpenTelemetry 的思路，但不引入其依赖。一次聊天会话是一棵树，每个节点是一个 **span**（一段有开始和结束的操作）；同一评测任务的一次重复运行可以包含多段聊天，靠评测任务 ID、重复序号和尝试 ID 关联：

```text
session                         一段完整对话
└─ turn                         用户的一轮消息
   ├─ coordinator               协调者处理这一轮
   │  ├─ llm                    协调者的模型调用
   │  ├─ task_update            任务清单变化（前 → 后）
   │  ├─ dispatch               派出子 Agent（任务说明）
   │  │  └─ subagent            子 Agent 执行
   │  │     ├─ llm
   │  │     ├─ tool             工具调用（参数、结果）
   │  │     │  └─ guard         护栏检查（放行 / 拦截 + 原因）
   │  │     └─ result           结构化返回
   │  ├─ confirmation           确认判定（用户原话、判定结果）
   │  └─ reply                  最终回复
   └─ state_snapshot            本轮结束时的任务状态
```

### span 公共字段

| 字段 | 说明 |
| --- | --- |
| `span_id` / `parent_id` | 组成树 |
| `session_id` / `turn` | 所属会话与轮次 |
| 评测关联字段 | 评测运行时记录 `run_id`、评测任务 ID、重复序号、尝试 ID；用于关联同一样本的多段聊天和补跑记录 |
| `kind` | 上面树中的类型 |
| `name` | 具体名称（如能力名、工具名） |
| `start` / `end` | 时间戳 |
| `status` | `ok` / `error` / `blocked` |
| `attrs` | 按类型不同的内容（见下） |

各类型的 `attrs`（初稿）：

| kind | attrs |
| --- | --- |
| `llm` | 模型、档位、输入消息引用、输出、token、费用、延迟 |
| `tool` | 工具名、参数、结果、读 / 写、执行状态（prepared / executed）、关联任务 ID、准备请求关联标识与操作 ID |
| `guard` | 护栏名、判定、原因 |
| `dispatch` | 能力名、实例 ID、任务 ID、任务说明 |
| `result` | 子 Agent 的结构化返回 |
| `task_update` | 变更前后的任务清单 |
| `confirmation` | 操作 ID、最近一次展示内容及所在回复、用户原话、逐操作判定结果与依据 |

### 实现要点

- 用 `contextvars` 记录当前 span，`with trace.span("tool", name): ...` 自动挂到父节点下；
- span 开始和结束各发一个事件，写入每会话一个 JSONL 文件，同时推送给订阅者（实时网页）；
- 完整提示词和模型输出单独存储，span 里只放引用；
- 在 LLM 调用层、工具网关、护栏、协调者分派这几个入口统一打点；
- 展示、确认、提交与核验记录通过操作 ID 关联，保留部分成功、拒绝、作废及失败原因；子 Agent 工具循环或每轮分派达到上限时写入 `guard` span；
- MVP 先提供命令行树状查看。

任务状态只持久化在 **LangGraph 检查点**中，不再维护一份独立任务状态表。轨迹中的 `state_snapshot`、`task_update` 是观测记录，不作为另一份可修改状态或恢复来源。`core/` 直接使用 LangGraph checkpointer，对话档案和摘要由小型存取模块保存；不为持久化预先增加 Protocol 层。

业务后端的操作记录是提交事实的权威来源。续办时重新验证身份，从检查点恢复任务，再按操作 ID 对账；准备已成功但操作 ID 未回写时，从恢复的任务 ID、修订号与动作类型确定性重算请求关联标识，找回操作，不要求每次准备前单独保存检查点。后端已提交而检查点未更新的操作补记为已提交，经过核验才能把写任务标为 `done`；待提交操作重新展示后才能接受确认。恢复流程详见 [02 Agent架构设计.md](<02 Agent架构设计.md#跨会话续办>)。

## 实验记录

| 项 | 约定 |
| --- | --- |
| 每次运行记录 | 代码版本、模型实际 API 标识与参数、档位映射、提示词版本、τ² 版本、随机种子、实验组别、具体任务清单及重复次数；中文包、政策、种子数据库和任务清单的校验值、转换版本 |
| 运行目录 | `runs/<run_id>/`：配置快照、每会话轨迹、检查点、业务库、结果汇总；一个计划样本以“评测任务 ID × 重复序号”标识，每次尝试另有 ID；同一 `run_id` 仅补未完成的样本，不覆盖已有尝试 |
| 隔离 | 每个评测任务的一次重复运行使用独立的业务数据与状态；同一次运行中的多段聊天共用该业务库和任务检查点，跨会话不重新初始化种子库。样本从头补跑时使用新的独立库，并保留旧尝试产物 |
| 结果 | 正式结果应补齐全部计划样本。Agent 业务失败计入已完成判分的失败样本，不能重跑覆盖；基础设施错误（超时、限流、网络等）重试后仍未完成运行或判分的，保留为待补跑，不计作 Agent 失败 |
| 未补齐的报告 | 单列完成率（已完成判分 / 计划样本），成功率与终态一致率只按已完成判分样本计算，同时列出样本数；任一题有效 n<k 时，不发布不完整的正式 pass^k 分数，详见 [03 实验设计.md](<03 实验设计.md#指标>) |
| 任务集冻结 | 困难评测集在针对 D 组调优前冻结，与开发种子隔离并检查近重复；保留任务及判分标注的固定版本。开发中查看 `retail_50` 失败案例的情况应如实披露 |
| 比较 | 按题配对，bootstrap 置信区间 |
| 费用与耗时 | 所有尝试、重试和补跑均保留调用账本与耗时，总成本包含这些开销；报告中单列基础设施重试 / 补跑的费用与耗时，可设预算上限 |
