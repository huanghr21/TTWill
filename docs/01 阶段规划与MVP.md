# 阶段规划与 MVP

> 最近更新：2026-11-12　｜　状态：草案；τ²-bench 已完成调研，见 [07 调研_tau2-bench.md](<07 调研_tau2-bench.md>)

## 总体思路

[00 项目定位.md](<00 项目定位.md>) 中的范围是**最终目标**。1～2 周内无法全部做完，因此分阶段推进：

- **先做最能体现 Agent 核心能力、结果最容易验证的部分**：订单服务 + 退换货；
- 每个阶段都形成一个**可运行、可评测的完整版本**，不留半成品；
- 后一阶段在前一阶段的架构上扩展，不推倒重来。

## 阶段划分

| 阶段 | 内容 | 业务环境 | 配套实验 | 预计投入 |
| --- | --- | --- | --- | --- |
| **一：MVP** | 订单服务 + 退换货（含同款换规格） | 自建业务后端（τ² retail 中文数据为种子、语义一致）+ τ²-bench 评测 | 主实验：2×2 对照（单/多 Agent × 有无任务状态） | 约 1～2 周 |
| 二 | 导购 + 用户画像 + 下单；跨商品换货 | 在自建后端上扩展商品与画像数据 | 画像消融实验 | 待定 |
| 三 | 自建模拟电商平台；退换货完整异步流程 | 自建平台 | 跨会话、异步事件下的继续办理 | 待定 |
| 后续 | 商家侧（处理售后 / 平台商家支持） | 自建平台 | 待定 | 待评估 |

> 第二、三阶段的顺序可以根据 MVP 后的情况调整。

### 为什么先做订单服务 + 退换货

| 理由 | 说明 |
| --- | --- |
| 直接补 EchoMind 的短板 | 从“给建议”变成“真正办成”，涉及会改动数据的操作 |
| 结果可以程序化判定 | 订单最终状态对不对，可以直接比较数据库，不依赖主观评分 |
| Agent 核心难点集中 | 多诉求拆分、追问补全、执行前确认、用户改口、中断后继续 |
| 有公开环境和基准 | τ²-bench retail 可以直接使用，省去搭平台和写评测器的时间 |

画像主要服务导购，所以放在第二阶段。

### 换货在两个阶段中的分工

| 类型 | 例子 | 需要的能力 | 阶段 |
| --- | --- | --- | --- |
| 同款换规格 | 耳机换黑色、鞋换大一码 | 查同一商品的其他规格（属性查询） | MVP |
| 跨商品换货 | 换成更轻的其他型号 | 导购检索与推荐 | 第二阶段 |

跨商品换货正好是第二阶段的跨场景演示用例：售后与导购在这里衔接。

## MVP 范围

### 业务功能

以 τ²-bench retail 实际提供的工具为准（已核实，15 个业务工具）：

| 类别 | 功能 |
| --- | --- |
| 身份与查询 | 通过邮箱或姓名+邮编验证身份；查询用户、订单、商品及规格 |
| 订单服务 | 解释订单状态；取消待发货订单；修改待发货订单的地址、商品规格、支付方式；修改用户默认地址 |
| 退换货 | 对已送达订单申请退货、同款换规格 |
| 其他 | 无法处理时转人工 |

MVP 中退换货按 τ²-bench 的方式处理：提交即生效，订单状态变为 `return requested` / `exchange requested`。审核、寄回、退款等异步环节放到第三阶段。

### Agent 能力

MVP 要重点做好的不是业务功能数量，而是这些**处理能力**：

| 能力 | 说明 |
| --- | --- |
| 复合诉求拆分 | 一句话中的多件事都能识别出来，逐一办理，不遗漏 |
| 条件与依赖处理 | “能换就换，没货就退”这类条件，先检查再执行 |
| 信息补全 | 缺少订单号、规格等关键信息时追问，不猜测 |
| 执行前确认 | 会改动数据的操作，先向用户说明并得到明确同意 |
| 改口处理 | 用户撤回或修改诉求时，更新任务，不执行过期的操作 |
| 结果核验 | 执行后重新查询业务数据，确认结果再告知用户 |
| 跨会话继续 | 中断后回来，能从保存的任务状态接着办 |

### 工程能力

- 任务状态持久化，支持中断恢复；
- 写操作防重复执行；
- 完整的调用轨迹，可回放失败案例；
- 一键运行评测，输出各对照组的指标。

Agent 架构与 EchoMind 模块的保留、替换、删除见 [02 Agent架构设计.md](<02 Agent架构设计.md>)。核心通过工具网关访问自建业务后端，τ²-bench 只用于评测。

### MVP 完成标准

1. 四个对照组（A / B / C / D）都能在同一环境、同一任务集上运行；
2. 官方 retail 任务与自建困难任务都能跑出可复现的结果；
3. 主实验结果整理成报告，含失败案例分析；
4. 有一个可交互的演示入口（命令行或简单网页即可）。

## 测试集扩充计划

### 为什么要扩充

τ²-bench 官方任务主要检验规则遵守与操作正确性。我们的特色在于**复合诉求、改口、中断**等更接近真实对话的情况，这部分需要自建任务来覆盖。这也是本项目和直接跑 τ²-bench（如 OrderWeave）拉开差异的地方。

### 困难任务类型

| 类型 | 例子 | 主要考察 |
| --- | --- | --- |
| 并列多诉求 | 这单耳机换黑色，另外那单地址填错了 | 是否遗漏；操作是否对应正确订单 |
| 条件依赖 | 能换就换，没货就退 | 是否先检查条件；是否只执行一个分支 |
| 顺序依赖 | 先取消这单，再把另一单改成同样地址 | 顺序与信息传递 |
| 中途改口 | ……算了，地址不改了，直接取消吧 | 旧任务是否撤销；过期操作是否被执行 |
| 信息缺失 | 只说“我那个耳机”，但有多笔相关订单 | 是否追问而不是猜测 |
| 跨会话继续 | 上次聊到一半，今天回来说“继续刚才的” | 能否恢复进度 |

### 构造方式（初步）

- 复用 τ²-bench 的数据库与任务格式：每个任务包含用户背景、用户指令和**预期的数据库最终状态**；
- 由 LLM 扮演用户，按任务指令与 Agent 对话；改口、中断等行为写进用户指令；
- 先人工编写少量种子任务，再用 LLM 辅助批量生成，**人工逐条核对预期状态**；
- 跨会话任务需要扩展运行方式：在指定轮次中断对话、清空上下文，再开新会话继续。

规模、生成方法与质量控制，在 Agent 本体完成后确定。

## 自建平台计划

### 什么时候需要自建

| 触发条件 | 说明 |
| --- | --- |
| 导购需要更丰富的商品数据 | 多品类、详细属性、商品描述、浏览/收藏行为，τ²-bench 预计没有 |
| 退换货完整异步流程 | 审核、寄回、收货、退款等由平台按时间或事件推进 |
| 演示需要 | 用户在“商城”中下单、看到订单变化，再找客服 |
| 商家侧扩展 | 需要商家身份与售后工单 |

### 初步设想

- **数据层**：按业务需求设计（商品描述、行为记录、售后工单状态机等），可参考 τ²-bench retail 的数据模型，但不受其约束；
- **业务接口**：沿用 MVP 后端的**工具网关接口**，平台扩展时 Agent 核心无需改动；业务规则在平台一侧校验；
- **事件模拟**：用定时任务或手动触发推进售后状态；
- **界面**：最简商城页面（商品、下单、订单列表）+ 客服对话窗口。

具体技术选型在 MVP 完成后讨论。

### 与 MVP 业务后端的关系

自建平台是一个**完整的小型购物模拟系统**，由 TTWill 自己设计，不复刻 τ²-bench。

它从 MVP 的业务后端起步（见 [02 Agent架构设计.md](<02 Agent架构设计.md#工具与业务后端>)）：

- **MVP**：自建 SQLite 业务库 + 订单与售后操作 + 两阶段写入；以 τ² 中文包数据为种子，操作语义与 τ² 保持一致，以便评测；
- **之后**：在同一个系统上扩展商品描述与行为数据、导购与下单、异步售后事件、商城界面、商家侧；数据结构按业务需要演进，不受 τ² 约束；
- τ²-bench 始终只是评测手段：通过快照导出判分。扩展后如果偏离了 τ² 的语义，就用 τ² 兼容的数据与规则运行评测。

## τ²-bench 调研结论（已完成）

详见 [07 调研_tau2-bench.md](<07 调研_tau2-bench.md>)。

- [x] 数据库：50 种商品 / 591 个规格、500 用户、1000 订单；无商品描述、无行为数据
- [x] 工具：15 个业务工具（7 查询 + 7 写操作 + 转人工）+ 计算器；政策要求执行前确认、单步执行
- [x] 任务：114 题（train 74 / test 40）；按数据库终态哈希判分，部分任务加 LLM 判定的断言
- [x] 版本：2.0.0 与 1.x 分数不可比，需锁定版本
- [x] 接入：继承 `HalfDuplexAgent` 并注册即可；四组对照可直接在同一批任务上运行
- [x] 扩展：数据库与工具可扩展，但会失去与排行榜的可比性；跨会话可借 `initial_state` 构造

### 任务划分

中文包的**实体映射表覆盖整个数据库**（500 个用户、全部地址、商品名和规格），只是任务文件仅本地化了 `retail_50` 这 50 道。其余 64 道题用到的用户和地址都能在映射表中找到，因此可以机械转换。

| 用途 | 任务 | 说明 |
| --- | --- | --- |
| 开发调试 | 其余 64 道（自行转换为中文版） | 日常迭代可从中分层抽 15～20 道；较大改动再跑全量 |
| 正式评测 | `retail_50`（官方中文版） | 官方 2.0 基准子集，结果可对外引用 |
| 困难任务 | 自建 | 少量种子用于开发，其余留作评测 |

**64 道题的转换方法**：写脚本，用官方映射表替换任务指令中的人名、地址、邮箱等实体，并把参考动作参数中的实体同样替换：user_id 换成中文别名，姓名、邮编、地址、邮箱换成映射后的值（否则参考侧重放出的数据库与中文库对不上）。**用官方 50 道题校验脚本**：对它们的英文原版运行脚本，结果与官方中文版逐字段比对，一致后再处理 64 道。

开发集与评测集使用同一份中文数据库，数据形态一致。这是个人项目，不要求严格隔离：开发中可以查看 `retail_50` 上的失败案例并据此改进；但报告中需如实说明，并以困难任务上的结果作为主实验的核心证据。

- [x] 模型：Agent、用户模拟器、判分默认都使用 DeepSeek V4.1 Flash（1017）；确有需要时（如强弱模型分层、判分可靠性）再引入 Claude / GPT 作为强模型
- [ ] 正式评测的运行次数 k（初定 4）；首轮运行后按实际费用确定预算
