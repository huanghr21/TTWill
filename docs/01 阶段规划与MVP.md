# 阶段规划与 MVP

> 最近更新：2026-11-13

## 总体思路

[00 项目定位.md](<00 项目定位.md>) 中的范围是**最终目标**。1～2 周内无法全部做完，因此分阶段推进：

- **先做最能体现 Agent 核心能力、结果最容易验证的部分**：订单服务 + 退换货；
- 每个阶段都形成一个**可运行、可评测的完整版本**，不留半成品；
- 后一阶段在前一阶段的架构上扩展，不推倒重来。

## 阶段划分

| 阶段 | 内容 | 业务环境 | 配套实验 | 预计投入 |
| --- | --- | --- | --- | --- |
| **一：MVP** | 订单服务 + 退换货（含同款换规格） | 自建业务后端（τ² retail 中文数据为种子、语义一致）+ τ²-bench 评测 | 主实验：2×2 对照（单/多 Agent × 有无任务状态） | 约 1～2 周 |
| 二 | 导购 + 用户画像 + 下单；跨商品换货 | 在自建后端上扩展商品与画像数据 | 画像消融实验 | 待定 |
| 三 | 自建模拟电商平台；退换货完整异步流程 | 自建平台 | 跨会话、异步事件下的继续办理 | 待定 |
| 后续 | 商家侧（处理售后 / 平台商家支持） | 自建平台 | 待定 | 待评估 |

> 第二、三阶段的顺序可以根据 MVP 后的情况调整。

### 为什么先做订单服务 + 退换货

| 理由 | 说明 |
| --- | --- |
| 直接补 EchoMind 的短板 | 从“给建议”变成“真正办成”，涉及会改动数据的操作 |
| 结果可以程序化判定 | 订单最终状态对不对，可以直接比较数据库，不依赖主观评分 |
| Agent 核心难点集中 | 多诉求拆分、追问补全、执行前确认、用户改口、中断后继续 |
| 有公开基准 | τ²-bench retail 提供数据、用户模拟器和判分，评测有公开参照 |

画像主要服务导购，所以放在第二阶段。

### 换货在两个阶段中的分工

| 类型 | 例子 | 需要的能力 | 阶段 |
| --- | --- | --- | --- |
| 同款换规格 | 耳机换黑色、鞋换大一码 | 查同一商品的其他规格（属性查询） | MVP |
| 跨商品换货 | 换成更轻的其他型号 | 导购检索与推荐 | 第二阶段 |

跨商品换货正好是第二阶段的跨场景演示用例：售后与导购在这里衔接。

## MVP 范围

### 业务功能

与 τ²-bench retail 的 15 个业务工具对应：

| 类别 | 功能 |
| --- | --- |
| 身份与查询 | 通过邮箱或姓名+邮编验证身份；查询用户、订单、商品及规格 |
| 订单服务 | 解释订单状态；取消待发货订单；修改待发货订单的地址、商品规格、支付方式；修改用户默认地址 |
| 退换货 | 对已送达订单申请退货、同款换规格 |
| 其他 | 无法处理时转人工 |

MVP 中退换货提交即生效，订单状态变为 `return requested` / `exchange requested`。审核、寄回、退款等异步环节放到第三阶段。

### Agent 能力

MVP 重点做好的是这些**处理能力**，而不是业务功能数量：

| 能力 | 说明 |
| --- | --- |
| 复合诉求拆分 | 一句话中的多件事都能识别出来，逐一办理，不遗漏 |
| 条件与依赖处理 | “能换就换，没货就退”这类条件，先检查再执行 |
| 信息补全 | 缺少订单号、规格等关键信息时追问，不猜测 |
| 执行前确认 | 会改动数据的操作，先向用户说明并得到明确同意 |
| 改口处理 | 用户撤回或修改诉求时，更新任务，不执行过期的操作 |
| 结果核验 | 执行后重新查询业务数据，确认结果再告知用户 |
| 跨会话继续 | 中断后回来，能从保存的任务状态接着办 |

架构见 [02 Agent架构设计.md](<02 Agent架构设计.md>)。

### MVP 完成标准

1. 项目本体能在命令行中完成上述业务，轨迹完整可查；
2. 四个对照组（A / B / C / D）能在同一环境、同一任务集上运行；
3. 官方任务与自建困难任务跑出可复现的结果，整理成含失败分析的报告。

## 测试集扩充计划

### 为什么要扩充

τ²-bench 官方任务主要检验规则遵守与操作正确性。本项目的重点是**复合诉求、改口、中断**这类更接近真实对话的情况，需要自建任务覆盖。

### 困难任务类型

| 类型 | 例子 | 主要考察 |
| --- | --- | --- |
| 并列多诉求 | 这单耳机换黑色，另外那单地址填错了 | 是否遗漏；操作是否对应正确订单 |
| 条件依赖 | 能换就换，没货就退 | 是否先检查条件；是否只执行一个分支 |
| 顺序依赖 | 先取消这单，再把另一单改成同样地址 | 顺序与信息传递 |
| 中途改口 | ……算了，地址不改了，直接取消吧 | 旧任务是否撤销；过期操作是否被执行 |
| 信息缺失 | 只说“我那个耳机”，但有多笔相关订单 | 是否追问而不是猜测 |
| 跨会话继续 | 上次聊到一半，今天回来说“继续刚才的” | 能否恢复进度 |

### 构造方式（初步）

- 复用 τ²-bench 的任务格式：用户背景、用户指令、**预期的数据库最终状态**；
- LLM 扮演用户，改口、中断等行为写进用户指令；
- 先人工写少量种子任务，再用 LLM 辅助扩写，**人工逐条核对预期状态**；
- 跨会话任务：在指定轮次中断、清空上下文，再开新会话继续。

规模与质量控制在本体完成后确定。

## 自建平台计划

自建平台是一个**完整的小型购物模拟系统**，由 TTWill 自己设计，从 MVP 的业务后端起步（见 [02 Agent架构设计.md](<02 Agent架构设计.md#工具与业务后端>)）：

- **MVP**：SQLite 业务库 + 订单与售后操作 + 两阶段写入；以 τ² 中文数据为初始数据，操作语义与 τ² 一致，以便评测；
- **之后**：在同一系统上扩展商品描述与行为数据、导购与下单、异步售后事件、商城界面、商家侧；数据结构按业务需要演进，不受 τ² 约束；
- **接口**：沿用工具网关，平台扩展时 Agent 核心无需改动；
- τ²-bench 始终只是评测手段。扩展后若偏离 τ² 语义，用 τ² 兼容的数据与规则运行评测。

| 扩展的触发条件 | 说明 |
| --- | --- |
| 导购需要更丰富的商品数据 | 多品类、详细属性、商品描述、浏览/收藏行为 |
| 退换货完整异步流程 | 审核、寄回、收货、退款由平台按时间或事件推进 |
| 演示需要 | 用户在“商城”中下单、看到订单变化，再找客服 |
| 商家侧扩展 | 需要商家身份与售后工单 |

具体技术选型在 MVP 完成后讨论。

## τ²-bench 使用约定

调研详情见 [07 调研_tau2-bench.md](<07 调研_tau2-bench.md>)。

| 项 | 约定 |
| --- | --- |
| 版本 | τ²-bench **2.0.0 + 中文语言包** |
| 模型 | Agent、用户模拟器、判分默认都用 DeepSeek V4.1 Flash（1017）；确有需要时再引入 Claude / GPT 作为强模型 |
| 运行次数 | 正式评测每题 k 次（初定 4），首轮运行后按实际费用确定预算 |

### 任务划分

中文包的**实体映射表覆盖整个数据库**（500 个用户、全部地址、商品名和规格），只是任务文件仅本地化了 `retail_50` 这 50 道。其余 64 道题用到的用户和地址都能在映射表中找到，因此可以机械转换。

| 用途 | 任务 | 说明 |
| --- | --- | --- |
| 开发调试 | 其余 64 道（自行转换为中文版） | 日常迭代可从中分层抽 15～20 道；较大改动再跑全量 |
| 正式评测 | `retail_50`（官方中文版） | 官方 2.0 基准子集，结果可对外引用 |
| 困难任务 | 自建 | 少量种子用于开发，其余留作评测 |

**64 道题的转换方法**：写脚本，用官方映射表替换任务指令中的人名、地址、邮箱等实体，并把参考动作参数中的实体同样替换：user_id 换成中文别名，姓名、邮编、地址、邮箱换成映射后的值（否则参考侧重放出的数据库与中文库对不上）。**用官方 50 道题校验脚本**：对它们的英文原版运行脚本，结果与官方中文版逐字段比对，一致后再处理 64 道。

开发集与评测集使用同一份中文数据库。这是个人项目，不要求严格隔离：开发中可以查看 `retail_50` 的失败案例并据此改进，但报告中需如实说明，并以困难任务上的结果作为主实验的核心证据。
