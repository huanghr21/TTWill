## 归因类别与迭代流程

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| 协议 | 工具协议让模型的合理动作无法执行 | 改协议或护栏，补回归测试 |
| 上下文 | 上下文臃肿、超预算或缺少关键信息 | 改上下文组装，补回归测试 |
| 政策理解 | 模型误解政策或业务规则 | 改 Skill / 提示词，在开发集上验证 |
| 能力 | 协议与上下文正常，模型仍做错 | 记录，计入实验结果 |
| 模拟器 | 模拟用户偏离任务指令 | 记录，单独统计 |

每轮迭代：在开发快速集上运行并保留 `run_id` → 按类别归因，一次只修一类 → 从真实轨迹摘出触发问题的模型输出，写成假模型回归测试 → 再跑快速集按题配对比较，有提升且无新退化才保留。

### F1.2：合并计划结束与首批分派

选择 `complete_plan(task_ids=[...])`：任务增改先在独立节点完成，随后一次决策即可结束计划并分派，省去单独的首批 `dispatch_tasks`。省略或空列表兼容原接口，后续分派仍用 `dispatch_tasks`。

参数与任务选择先校验，代码再独立确认并核验旧操作，最后按最新状态与同单占用分派；新操作仍等待下一条用户消息确认。检查点边界、身份和确认护栏保持原约定。格式错误继续计入轮数：免计需要另加总尝试上限，否则连续错误会失去终止保障，也可能增加上下文噪声。

先完成这一协议修复，再测 F1.3。预计必要调用数会减少；拒绝次数、上下文占用和成功率是否改善，仍需开发快速集按题配对验证。

### F1.3：思考内容必须回传

[DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)规定：请求带 `tools` 时，**所有历史轮次**的 `reasoning_content` 都要原样回传，包括没有调用工具的回复，缺失会返回 400。因此最初“剥离思考内容”的方案已撤回，完整模型消息照常保存和回传。

必须保留的是仍在上下文中的历史消息协议字段，25k 是这次请求的实测占用，并非固定大小。减少模型调用或按完整旧轮次摘要都可能降低它；后续按以下方向测量后再决定：

- 减少失败噪声：格式拒绝、工具错误（先测 F1.2 修复后的实际变化）；
- 精简任务快照：读任务 `facts` 中的完整订单 JSON 改为摘要或引用；
- 更早触发整轮摘要：摘要会整体移除旧轮次的调用、结果及其思考内容，符合协议；
- 调整思考强度或预算：会影响实验配置，需先确认。

预算暂保持 64000 字符。字符数与 token 的换算尚未验证。

### F2 第二轮修复方案（2026-11-19）

逐条复核 `88` 第 7 轮决策后确定。六项修复已生效（订单号统一、只读查询、无待确认时直接回复、全只读批量执行、思考关闭），但两题都卡在确认判定之前，20 题门槛仍未满足。

#### R1 确认判定不能被分派参数挡住

**现状**：`complete_plan` 的执行顺序是「校验 `task_ids` → 判定用户确认 → 分派」（`coordinator.py` 的 `_execute_call`，注释写明“先拒绝无效选择，避免错误参数触发用户确认对应的业务提交”）。`88` 第 7 轮用户已说“全部确认”，模型调用 `complete_plan(task_ids=[已展示的取消任务])`；该任务状态为 `pending_confirm`，不满足“可分派”条件，整次调用被拒，**确认判定根本没有执行**。用户随后又确认 4 次，全部同样落空。

**修复**：确认判定始终执行。`task_ids` 中的非法项（不存在、重复、状态不符）只是不参与分派，把原因写进返回结果；只有参数结构本身不合法（如不是对象、缺必填字段）才整次拒绝。分派参数错误不得影响用户授权的处理，也不得因此消耗一次确认机会。

**保留的理由**：原注释担心“错误参数触发提交”指的是**分派参数影响到了提交内容**。本修复中提交仍只凭前一条回复实际展示的操作和操作 ID，与 `task_ids` 无关，因此不放宽任何授权边界。

#### R2 内容未变化的更新不得作废已准备操作

**现状**：`TaskStore` 对任何更新都无条件 `task.revision += 1` 并清空 `operation_ids`。`88` 第 7 轮模型被拒后重发完全相同的任务内容，已准备好的取消操作因此作废，子 Agent 重新准备，上下文从 41k 涨到 73k。

**修复**：更新前比较可见字段（`capability`、`action`、`order_id`、`condition`、`instruction`、`missing`）。完全一致时视为无变化，不递增修订、不作废操作、不重新准备，返回“无变化”。有实质变化时维持现行语义。

#### R3 任务快照只在编译器注入一份

**现状**：`update_tasks`、`complete_plan`、`dispatch` 的返回值都附带完整任务快照，进入历史后每轮重复发送；编译器每轮另注入一份最新权威快照。`88` 峰值请求中工具结果里的 `tasks` 与 `dispatched` 各约 8.5k 字符，合计约占 63.9k 上下文的 27%；快照内 `facts` 还内嵌完整订单 JSON。

**修复**：

- 协调工具与分派的返回值只给变化摘要（任务 ID、状态、原因），不再附完整快照；需要全貌时读编译器注入的那一份；
- 编译器注入的快照中，`facts` 只保留动作、关键标识与结果摘要，不内嵌完整业务对象；`actions` 同时裁剪为动作、操作引用、参数、状态及原因，移除内嵌完整预览与执行结果。88 峰值快照中两者分别为 2,800 与 5,799 字符，不能只处理 `facts`；
- 精简视图覆盖持久运行时、内存入口及子 Agent 输入；内存入口每次请求只组装一份最新状态，不在历史里逐步追加合成快照。子 Agent 需要细节时重新查询。完整任务、检查点、档案、轨迹及确认核验数据保留原值。

不改 `max_chars`、`recent_turns` 与摘要触发策略；先看本项修完后的实测占用。

#### R4 修改预览只列变化的商品

**现状**：`_PREVIEW_FIELDS["modify_pending_order_items"]` 取修改后订单的全部 `items`。`60` 题只改耳机，预览却列出彩妆、办公椅、音箱，模拟用户因此追问整单是否都会改。

### F3 回复层与上下文组装修复方案（2026-11-19）

依据固定 20 题基线的逐题审计，并对照 `coordinator.py`、`context.py`、`task_view.py` 和 24、28 两题的真实请求确定。规则以 02 的[回复的生成](<02 Agent架构设计.md#回复的生成>)和[上下文编译](<02 Agent架构设计.md#上下文编译>)为准，本节给出现状证据、修改点和验收标准。

| 阶段 | 内容 | 类别 |

#### R5 回复由模型撰写，代码只附确认卡片（F3a）

**现状**：`Coordinator._reply`（`coordinator.py`）逐个任务输出状态模板，模型的 `message_hint` 只在一个任务都没有时才使用（`if not lines`）。也就是说，只要会话里有任务，模型写的回答就会被整段丢弃；模型的纯文本输出也按 `Reply(message_hint=text)` 处理，结果相同。用户收到的文本就是 `result["reply"]`（`bench/agent.py`），中间没有再经过模型。此外，模板本身也不适合给用户看：只读任务完成时直接输出 `json.dumps(fact["result"])`，预览由 `presentation.operation_content` 输出两段缩进 JSON，终态任务的状态和撤销理由每轮重复一遍。

证据：

- 24（`attempts/016`）：模型在第 3 轮已经答出两件 T 恤的颜色、尺码和材质（`reply` 参数及第 39、42、45 条纯文本），用户 4 次只收到“#W3561391 · 取消订单：已撤销。用户改口……”，最后要求转人工；
- 同题第 2 轮用了 8 次决策，分派成功的同时碰到 `max_rounds`，`stop_turn` 在一份有效预览前写了“抱歉，这次处理没有完成”；
- 基线受影响的题：失败 31、3、4、24、28，成功 33、48、82、92。

**修改**：

1. `Reply` 改为 `message`（必填非空）+ `show_task_ids`。最终回复 = `message`；本次有展示操作时，再接 `\n\n` 和确认卡片。纯文本输出按同样规则处理。
2. 删除逐任务状态行、`missing` 行、撤销 / 失败理由行和只读结果 JSON 的输出。
3. `operation_content` 改为自然语言逐行格式（`· 字段：值`，列表逐项缩进），保留现有字段翻译及商品修改的改动项裁剪，不再输出 JSON。确认方式提示保持现有文字。`displayed[].content` 存卡片原文；另存完整实际回复 `last_reply`，确认判定器用完整上一回复消歧，候选操作仍仅来自卡片。实际对话不以精确短语规则跳过正文消歧；正文另有追问时，用户“好的”不能直接授权卡片操作。跨会话同时清除旧卡片与旧完整回复。
4. 完成表述观察：固定词表每次命中均记录 `reply_claim` span（含正文、命中词、相关动作和任务核验状态），**不拦截**。`done` 不豁免记录，退货申请完成也不等于退款到账；首轮由人工判断真实违规和误报。
5. `stop_turn`：仍有可确认操作时使用 02 规定的说明文字并附卡片，否则沿用 `STOP_NOTICE`。
6. 改名：子 Agent `finish` 和 `Task` 的 `message_hint` 改为 `note`，协调者 `Reply` 的改为 `message`；同步系统提示、子 Agent 提示、演示脚本与测试。旧运行目录的检查点不需要兼容。
7. 系统提示按 02 补充正文的写法要求：自然语言、不贴 JSON 和字段名、不复述卡片参数、未核验不说完成、变化只说一次。

不改 `max_rounds`、`max_steps`、上下文预算。确认判定器仅补完整回复消歧及相应回归，既有操作范围、修订和参数核对不变。F3a 保证已获准的回复原样送达，仍保留先 `complete_plan` 再回复的阶段约束；阶段拒绝循环不在本轮自动消除，复测后单列统计。

#### R6 跨轮只保留对话（F3b）

**现状**：`PersistentRuntime._advance` 把每次决策的全部往返写入档案，`ContextCompiler.compile` 跨轮读取档案原文，最近 4 轮完整保留模型的工具调用、工具结果、错误反馈和 `reply` 参数，再加代码生成的回复。24 题的最后一次请求中，历史消息有 46 条，其中工具往返 29 条、12,265 字符，对话只有 2,212 字符；第 39、40 条是连在一起的两条 assistant 消息（模型的纯文本回答 + 代码模板），模型看到的历史和用户看到的不一致。28 题的最大请求中，跨轮工具往返 28,058 字符，对话 8,324 字符，任务快照 10,590 字符。

**修改**：档案仍只追加、完整保存。档案为每轮的用户原话和最终回复打上可识别的标记；编译器跨轮只读这两类条目，摘要输入也只用对话。本轮往返（⑤）完整保留。不改 `recent_turns`，它的含义变为“最近 4 轮对话不摘要”。

#### R7 业务数据区（F3b）

**现状**：跨轮工具结果去掉之后，模型需要的业务数据要另有来源。现在同一实体会被反复完整查询：24 题中 `#W9609649` 在最近 4 轮里查了两次，每份 1,297 字符。

**修改**：按 02 的“③ 业务数据区”实现，包括来源、实体键去重、写后刷新、每轮开始时生成、`data_max_chars=16000` 上限、存入检查点、跨会话清空。新增配置项写入 `config.toml` 的 `[context]`。数据区作为一条 system 消息放在对话记录之后、任务区之前。本轮子 Agent 查询及核验读取，由代码作为协调工具返回的业务增量送入⑤，按实体去重；协调者直接查询已在⑤，不重复注入。新结果优先于轮初数据，下一轮合并③，保证同轮回复可使用真实业务值。

#### R8 任务区投影与终态清理（F3b）

**现状**：任务进入终态后不会移出，每次请求都以完整视图出现，其中含 `actions` 历史（包括已作废的 prepare / reject 记录）和 `facts`。`_verify` 只修改 `status`，`missing` 保留，导致“已完成仍显示需要补充”。24 题中一个已撤销任务占 1,441 字符。

**修改**：

1. `task_view` 按 02 的“④ 任务区”分活跃 / 终态两种投影，持久运行时与内存入口共用；子 Agent 的已有事实仍用 `facts_view`。
2. 任务进入 `done`、`cancelled`、`failed` 时清空 `missing` 与 `note`（`_verify`、`TaskStore._plan` 的撤销分支、各失败分支）。
3. 检查点、轨迹和核验用的完整任务不裁剪。

#### 验收

F3a：

1. 离线回归：
   - 有任务时，最终回复以 `message` 原文开头；没有展示操作时，最终回复与 `message` 完全相同；
   - 有展示操作时，卡片不使用 JSON 结构（业务原值中的合法引号等原样保留），`displayed[].content` 等于卡片原文；确认判定器能读取完整上一回复、卡片和用户原话，但不能从正文增加操作；
   - 正文“需要转人工吗？”加取消卡片后收到“好的”不自动提交；明确指向取消卡片的授权仍可提交，跨会话旧回复不能作为授权；
   - 只读任务完成后，回复中没有查询结果的 JSON；
   - 用 24 题第 3 轮的模型输出写回放测试：用户收到 T 恤回答，而不是“已撤销”；
   - 完成表述命中时均写 `reply_claim` span，不拒绝；写任务 `done` 后说“已退款”仍留下观察证据；
   - `stop_turn` 时有有效卡片的情况下，不出现“这次处理没有完成”。
2. 在 24、4 两题上冒烟，人工核对回复内容。
