# 失败案例与修复记录

> 最近更新：2026-11-17
>
> 记录真实模型运行中发现的失败、归因与修复。每个案例只写可从轨迹核实的事实；修复须附离线回归测试。评测题（`retail_50`、困难任务集）上的失败只用于归因，不针对单题调提示词。

## 归因类别

| 类别 | 含义 | 处理方式 |
| --- | --- | --- |
| 协议 | 协调 / 子 Agent 的工具协议让模型的合理动作无法执行 | 改协议或护栏，补回归测试 |
| 上下文 | 上下文臃肿、超预算或重要信息缺失 | 改上下文组装，补回归测试 |
| 政策理解 | 模型误解政策或业务规则 | 改 Skill / 提示词，在开发集上验证 |
| 能力 | 协议和上下文都正常，模型仍做错 | 记录，作为实验结果的一部分 |
| 模拟器 | 模拟用户偏离任务指令 | 记录，失败分析中单独统计 |

## 迭代流程

1. 在开发快速集上运行，保留 `run_id`；
2. 按上表归类失败，每次只修一类；
3. 从真实轨迹摘出触发问题的模型输出，写成假模型脚本的离线回归测试；
4. 再跑快速集，按题配对比较：有提升且无新退化才保留修改。

## F1：`6_zh_identity` 首次真实运行（2026-11-17）

产物：`runs/step7-deepseek-task6-20261117-attempt-001/`。结果：`user_stop`，数据库无变化，奖励 0。53 次模型调用全部正常返回。

### F1.1 协议：身份验证前无法回复用户

用户首句只说要换货，没给身份信息。协调者此时只开放 `find_user_id_*` 与 `complete_plan`，`reply` 要求先 `complete_plan`，而 `complete_plan` 只在验证后才有意义。模型 8 次都正确地用文字请用户提供邮箱或姓名 + 邮编，全部被格式护栏拒绝，耗尽 8 轮后把内部错误发给用户。同样情况连续发生两轮。

### F1.2 协议：计划 → 确认 → 分派的强顺序反复被拒

验证后，模型多次在 `complete_plan` 之前分派、或在同一轮再次 `complete_plan`，分别被拒；还出现一次同时调用多个工具。每次被拒都消耗一轮，并在上下文中追加错误消息。全程 20 次格式拒绝、6 次协调工具拒绝。

### F1.3 上下文：思考内容与重复状态占用预算

最大一次协调请求约 59k 字符（预算 64k，按字符计），构成如下：

| 部分 | 字符数 | 说明 |
| --- | --- | --- |
| 历史中模型的 `reasoning_content` | 约 25k | DeepSeek 思考模式的工具协议要求回传，不能直接删除 |
| 本轮往返 | 约 13k | 含格式拒绝、工具错误及重复的任务快照 |
| system 提示（协调规则 + 通用政策 + 能力目录） | 4.4k | |
| 权威任务快照 | 4.0k | 读任务的 `facts` 内嵌完整订单 JSON |
| 工具定义 | 3.6k | |
| 内部错误回复、格式提示 | 约 3k | 失败本身产生的噪声 |

修复审阅发现，原方案把思考内容当成无用字段直接删除，会破坏当前使用的 API 协议。[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/thinking_mode/)要求带 `tools` 的思考模式请求回传历史 `reasoning_content`，包括之前用户轮次和没有调用工具的模型回复；缺失可能导致 HTTP 400。本轮保留 `high` 思考配置，撤回字段剥离，补回传与历史压缩边界的回归测试。

重复状态、大结果和失败噪声仍是后续压缩候选，但应分别测量并验证。原先“压缩到 20k 字符以内”和字符对应 token 的判断未经验证，不作为验收结论；预算保持 64000 字符。

### F1.4 协议：子 Agent 不知道身份已验证

身份验证后派出的查询子 Agent 有 2/3 返回 `need_info`，要求用户提供邮箱或姓名 + 邮编。原因：子 Agent 的提示词包含通用政策中“对话开始时必须验证身份”的条款，却没有告诉它身份已由协调者验证。子 Agent 也没有查找用户的工具，只能返回缺信息。

### F1.5 回复：内部错误原样展示给用户

“协调者达到本轮上限 8”“上下文编译无法继续……”直接出现在用户回复中，模拟用户随后认为系统故障并退出。

### F1.6 能力（未修复，仅记录）

模型首次调用 `find_user_id_by_name_zip` 时把姓和名填反（郑 / 梅），失败后自行纠正。属于模型能力范围；工具参数描述已注明“名”“姓”，暂不处理。

### 修复

| 问题 | 修复 | 回归测试 |
| --- | --- | --- |
| F1.1 | 身份验证前开放 `reply`，允许不经计划直接回复（此时没有任务可推进） | 见下方“修复验证” |
| F1.1 / F1.2 | 模型未调用工具、但给出了文字时：若当前允许回复，视为 `reply(message_hint=文字)`；否则按格式错误处理 | 同上 |
| F1.3 | 撤回全量剥离 `reasoning_content` 的改动；保留完整模型消息，验证工具往返、历史引用化及整轮摘要的协议边界 | 同上 |
| F1.4 | 子 Agent 任务说明注明“用户身份已由协调者验证为 X，不要再要求用户验证” | 同上 |
| F1.5 | 超限 / 上下文失败时使用客服话术；内部原因保存在任务 `reason` 与轨迹，代码维护 `reason_internal` 标记，跨轮与恢复后继续隐藏 | 同上 |

### 接力审阅结论

接力前工作区已有未提交实现及两处测试断言调整，尚未完成全量验证。本次按用户要求审阅后，保留身份前回复、派工身份说明与用户可见错误分离的方向，作以下修正：

| 范围 | 审阅后的实现 |
| --- | --- |
| `core/coordinator.py` | 未验证时只开放身份查询与 `reply`，执行路径也拒绝提前 `complete_plan`。纯文本仅在同阶段允许回复、且没有可推进任务时接受；验证后的计划、确认及分派顺序不放宽 |
| `llm/types.py`、`core/subagent.py` | 撤回 `replay_message` 及字段剥离，继续保留服务返回的完整消息；本轮这两个源码文件没有最终改动 |
| `core/runtime.py` | 纯文本已是实际回复时只归档一次完整模型消息，避免重复追加相同的合成回复；任务状态生成的回复仍单独保存 |
| `core/tasks.py`、`core/coordinator.py`、`core/recovery.py` | 用代码维护的 `reason_internal` 随任务检查点保存原因可见性；原来的单次 `hidden_reason` 参数不能防止下一轮泄露，已移除。任务修订及业务结果重写原因时同步重置标记 |
| 回复与任务记录 | 固定客服话术只表达当前未完成、可重试或申请人工，不声称已经转人工。具体内部原因保留在任务和轨迹，业务拒绝原因仍可向用户解释 |

两处既有测试按 F1.5 的新用户可见行为调整，并继续断言内部原因、准备状态和确认范围。新增测试覆盖协议与恢复边界，不能用这些离线结果推断真实任务成功率。

旧检查点缺少 `reason_internal` 时仍可加载，默认沿用旧原因的可见性；本轮不猜测分类或改写既有档案。新增内部原因标记才提供跨轮和恢复后的展示隔离。
