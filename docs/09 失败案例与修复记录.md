## 归因类别与迭代流程

| 类别 | 含义 | 处理 |
| --- | --- | --- |
| 协议 | 工具协议让模型的合理动作无法执行 | 改协议或护栏，补回归测试 |
| 上下文 | 上下文臃肿、超预算或缺少关键信息 | 改上下文组装，补回归测试 |
| 政策理解 | 模型误解政策或业务规则 | 改 Skill / 提示词 / 政策接入，在开发集上验证 |
| 能力 | 协议与上下文正常，模型仍做错 | 记录，计入实验结果 |
| 模拟器 | 模拟用户或判分偏离任务本意 | 记录，单独统计 |

每轮迭代：在开发快速集上运行并保留 `run_id` → 按类别归因，一次只修一类 → 从真实轨迹摘出触发问题的模型输出，写成假模型回归测试 → 再跑快速集按题配对比较，有提升且无新退化才保留。

### 统计口径

- **指标**：`completion_rate`、`task_success_rate`（含适用的自然语言断言）、`db_match_rate`。官方分数照原样保留，人工审计的结论单列，不回写分数。一道题可能同时有多个问题，“主类”只记一个，其余记为并存，不重复计入失败题数。
- **样本**：每批 20 题各跑 1 次，种子 0。**单批里个别题的成败翻转，不足以把分数变化归因到某项修改**，要结合逐题审计来判断。
- **拒绝**：格式拒绝指 `coordinator_format` guard，工具拒绝指 `coordinator_tool` guard，都不含网关、子 Agent 的 guard 和循环上限。
- **上下文字符**：按 `ensure_ascii=False` 的紧凑 JSON 编码计算 `{"messages", "tools"}`，不是 token 数。拆成思考、本轮往返、错误反馈、任务快照、业务数据、摘要、历史、系统提示、工具定义和 JSON 开销，各项互斥、可以相加。
- **姓名错误**：分两类统计，一是严格的姓、名填反，二是其他拆分错误（如全名同时填入姓和名）。
- **可复核性**：每批启动前都核对代码和提示资源的哈希、配置的 SHA-256，运行期间不改代码；目前所有批次都满足，下文不再逐次说明。没有配置模型单价，费用均未知。

## F1：`6_zh_identity` 首次真实运行（2026-11-17）

53 次调用全部正常返回，以 `user_stop` 结束，数据库没有变化。失败过程是协调者被协议规则连续拒绝（格式拒绝 20 次、工具拒绝 6 次），随后触发轮数和上下文上限。最大的一次请求约 59k 字符，其中历史思考内容约 25k。首轮修复后，640 项离线测试通过。

### F1.2：合并计划结束与首批分派

`complete_plan(task_ids=[...])` 在同一次决策里结束计划并分派已有任务；省略或传空列表时与原接口兼容。代码先独立判定确认并核验旧操作，再按最新状态和同单占用情况分派，新准备的操作仍要等下一条用户消息确认。格式错误照样计入轮数，以保证连续出错时能终止。

## F3 评估与讨论结论（2026-11-20）

### F3a：接受

R5 修的是一个正确性问题：设计本意是让回复送达用户，实现时却把它覆盖掉了。判断它是否成立，应该看回复是否送达、授权有没有被削弱，而不是看分数：24、28 的回答已经实际送达，格式拒绝从 34 次降到 20 次，所有提交都能追溯到卡片之后的明确授权。

成功率没有上升，原因有两个：

- **失败发生了转移。** 一道题往往有好几道坎，F3a 去掉了协议这一道，3、4、31、101 都走得更远，但又卡在下一道（姓名、地址字段、判分、模拟器）。主类里的协议从 4 题降到 0 题，转成了能力类和模拟器类。
- **模型的沟通策略开始影响结果。** 77 和 96 表面上是模拟用户跑偏，实际都是模型的正文先给了用户一个出口（主动提出转人工、把选项拆开问）。在 001 里模板挡住了这些话，所以这是 F3a 暴露出来的新问题，不是退化。

同一阶段还改了确认判定器的输入，这部分要单独观察：4（明确确认被判为拒绝）、92（确认被判为修改）和 F3b 冒烟中的“别的别动”都属于判定器问题。

### F3b：数据和状态保住了，过程被拿掉了

上下文变短本身不说明什么，要看的是精简有没有拿掉模型需要的信息。把模型需要的信息分成三类：

| 信息 | F3b 处理 | 结论 |
| --- | --- | --- |
| 业务数据（订单、商品） | 业务数据区，按实体去重 | 保住了，没有发现缺数据导致的错误 |
| 状态（任务、进度） | 任务区 | 保住了 |
| 过程（我上一轮做了哪些调用） | 跨轮全部去掉 | **被拿掉了** |

证据是 28 第三单出错的那次请求（`attempts/020/models/da4549a7…`）。当时任务区只列出两单已完成的退货，没有第三单；业务数据区里有第三单的订单。模型这一轮的第一个输出就是“您的退货申请已提交成功”。历史里只剩“正文征求确认 → 用户说确认 → 成功”这样的对话，看不到中间的 `update_tasks`、`dispatch`、`complete_plan`，模型照着表面模式往下接了。粗略统计（正则匹配，仅供参考）：正文里自行征求确认的次数，001 为 18，002 为 10，003 为 32。

其余 4 道由成功转为失败的题，95 是老的协议问题，48 是三批都出现过的政策错误，60、82 是参考答案的局限，都和 F3b 无关。R7、R8 暂时接受；R6 先保留，等政策修复后再看过程信息的缺失是否还会造成问题。

### 政策接入核对

28 的直接诱因是政策：协调者原样收到了 τ² 的 “Before taking any action that updates the database … obtain explicit user confirmation (yes) to proceed”。逐条核对完整政策和 7 个 Skill 后，发现三类冲突：

| 冲突类型 | 条款 | 现状 | 证据 |
| --- | --- | --- | --- |
| **执行者错位**：架构已经执行了，政策仍要模型再做一遍 | 写操作前列出详情、取得 yes；改商品 / 换货时“提醒用户确认已给全” | 协调者和子 Agent 都收到原文；D 组的协调者没有提交能力，确认由卡片和判定器完成 | 正文自行征求确认，用户确认两三次；28 虚构完成 |
| **可见性错位**：规则只给了不对话的一方 | 取消、修改待发货订单、改支付、改商品、退货、换货各章（约 3.3k 字符） | 只在子 Agent 的 Skill 里，**协调者看不到**。F2 把协调者改成了负责解释、追问的对话主体，政策拆分却没有跟着调整 | 三批反复出现：“退换货只能整单”（82、31、48），“可以部分删除 / 部分取消”（34、28） |
| **架构缺失**：政策要求的能力不存在 | 转人工：先调用 `transfer_to_human_agents`，再发固定话术 | 协调者没有这个工具；02 的能力表却写着协调者负责转人工 | 模型只能在正文里说“可以转人工”；多题以模拟器 `TRANSFER` 结束 |

其余条款（服务范围、身份验证、只服务一个用户、不编造、领域基础、通用动作规则）原样适用，不冲突。通用规则 “Exchange or modify order tools can only be called once per order” 由“订单 × 动作”聚合和 Skill 承担；96 把它误读成“一单合计只能改一次”，所以动作章节对协调者可见之后，这类误读也要再观察。

修复方案见 [F4 政策接入修复方案](#f4-政策接入修复方案2026-11-20)。

**修完政策还要不要改上下文结构**：暂时不改。政策修复去掉的是诱因：卡片成为唯一的确认点之后，历史里的对话模式会变成“卡片 → 确认 → 成功”，模型照着它接下去也是正确的。业务数据和状态已经核实完整，只有过程信息被拿掉，而它的危害目前只在与政策冲突叠加时观察到。按“一次只修一类”，F4 只修政策接入，同时记录两个新指标：**无卡片确认**（用户说了确认，上一条回复却没有卡片）和**虚构完成**（正文声称某张订单已完成，该单却没有已核验的写任务）。如果修完后这两个指标仍然存在，再考虑在跨轮历史里保留过程骨架（工具名、参数和简短结果，不含数据正文），或把虚构完成改为按订单号拦截。

| 问题 | 证据 | 类别 | 处理思路（待讨论） |

## F4 政策接入修复方案（2026-11-20）

依据上面的政策接入核对确定，规则见 [02 · 政策拆分](<02 Agent架构设计.md#政策拆分>) 和 [02 · 转人工](<02 Agent架构设计.md#转人工>)。三项都来自同一次核对，作为一个阶段实现和验证；转人工的效果用单独的指标观察。

### P1 确认条款按组排除

**修改**：`PROTOCOL_EXCLUSIONS` 增加 “Before taking any action that updates the database (cancel, modify, return, exchange), you must list the action details and obtain explicit user confirmation (yes) to proceed.” 这一项，理由写“由代码执行确认的组中，列出详情由卡片完成、取得 yes 由判定器完成”。协调者系统提示加入 02 规定的架构说明。子 Agent 也会收到通用政策，同样不再看到这条。

目前只实现了 D 组，排除清单仍是单份配置，不为 A / B 组提前做分组机制；第 8 步实现 A / B 组和 “D − 确认”消融时，它们必须使用保留这条的清单（03 已写明）。

### P2 协调者常驻全部动作章节

**修改**：协调者系统提示改为常驻排除后的完整政策原文（通用部分 + 全部动作章节，原文不改写），不再只用未被 Skill 引用的章节。子 Agent 的提示和 Skill 门控不变：仍只列本能力的 Skill 目录，加载后才解锁写工具。

预计协调者系统提示增加约 3.3k 字符，位于稳定前缀。

### P3 转人工工具

**修改**：按 02 的“转人工”一节实现 `transfer_to_human(summary, message)`，包括：阶段约束与 `reply` 一致；转接前对账、核验已提交操作、作废准备项；未到终态的任务改为 `transferred`；代码追加固定话术；`handoff` span 与检查点记录；转接后的用户消息由代码固定回复，不调用模型。`transferred` 是终态，在任务区按终态一行投影。适配层不向 τ² 轨迹写入工具调用（计分不含动作），只把回复文本交给模拟用户。

### 观察指标

P1、P2 都只改提示内容，不改协议，所以效果只能靠运行指标判断。分析脚本新增：

| 指标 | 定义 | 统计方式 |
| --- | --- | --- |
| 无卡片确认 | 用户原话是确认（命中确认短语表），但上一条回复没有卡片 | 脚本初筛，逐条人工核对 |
| 虚构完成 | `reply_claim` 中的 `unsupported_orders` 非空：正文说某张订单已完成，该单却没有已核验的写任务 | 脚本统计，人工排除历史事实误报 |
| 政策表述错误 | 回复中与政策不符的规则说明，如“退换货只能整单”“可以部分取消” | 逐题审计 |
| 转人工 | 转接次数、时机，以及是否符合政策条件 | 逐题审计 |

### 验收

1. 离线回归：
   - 协调者和子 Agent 的提示都不含确认条款原文；协调者提示含架构说明和全部动作章节原文；子 Agent 在加载 Skill 前调用写工具仍被拒绝；
   - 转人工：有有效展示时须先 `complete_plan`；已提交未核验的操作先核验；准备项被拒绝、订单占用释放；任务变为 `transferred`；回复末尾是固定话术；转接后的消息得到固定回复且没有模型调用；检查点恢复后仍是已转人工；
   - `reply_claim` 对 28 题第三单那类回复（正文说已提交，该订单没有写任务）标出 `unsupported_orders`。
2. 冒烟：28（正文确认、虚构完成）、48（退货能否部分商品）、开发集 10 或 12（参考动作含转人工），人工核对回复。
3. 提交代码后跑 `runs/dev-quick-004`，与 `dev-quick-003` 按题配对比较，报告上面四项指标。保持关闭思考、种子 0 和现有预算。

**判断标准**：无卡片确认和虚构完成接近消失、政策表述错误明显减少，P1、P2 即视为有效。若这两个指标仍然存在，再考虑在跨轮历史里保留过程骨架（工具名、参数和简短结果）或按订单号拦截虚构完成，这属于上下文类或协议类修改，下一轮单独进行。
