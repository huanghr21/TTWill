# Agent 架构设计

> 最近更新：2026-11-16
>
> 设计原则：**按产品需求设计，τ²-bench 只是接入的一种评测环境**，通过适配层对接，不影响核心架构。

## 核心决策

| # | 决策 | 说明 |
| --- | --- | --- |
| 1 | **保留并改造多 Agent**，不退回单 Agent | 改造重点是协调方式，不是简单换角色 |
| 2 | **预设能力 + 动态编排**，参照 Claude Code 的子 Agent 机制 | 能力类型由开发者预设；何时调用、调用几个、写什么任务说明由协调者决定 |
| 3 | 工具权限**完全由能力类型决定**，与 Claude Code 一致 | 调用时不能指定或收窄工具；不做自由编排，也不为此进一步细拆类型 |
| 4 | 子 Agent 返回**结构化结果**（相对 Claude Code 的改进） | 协调者据此核对任务、生成回复，避免转述时把事实改错 |
| 5 | 任务清单由协调者维护，代码护栏保证写操作安全 | LLM 决定做什么，代码保证不越界 |
| 6 | 工具分两层：Agent 层定义工具，**自建业务后端**实现业务；中间通过工具网关连接 | 后端以 τ² 中文数据为初始数据、语义与 τ² 一致以便评测，并作为自建购物平台的起点 |
| 7 | 运行时**可暂停、可恢复**；协调层使用 LangGraph | 统一满足等待用户确认、跨会话继续两种需求 |
| 8 | 记忆分层，**任务状态是可信记忆**；上下文每轮由代码组装，超预算时才摘要 | 正常情况下不增加模型调用 |
| 9 | 政策拆为 Skill 按需加载（参照 Claude Code）；RAG 第二阶段用于导购主线 | MVP 没有需要检索的非结构化内容 |

## 为什么要改多 Agent 的协调方式

EchoMind 与 OrderWeave（同源代码）都采用“意图识别 → 选一主一辅 → 执行一次 → Composer 合成”：

| 问题 | 表现 |
| --- | --- |
| 角色划分不贴合业务 | general / technical / billing / escalation 是通用客服角色，与电商的订单、售后、导购不对应 |
| 单意图分派 | 一句话中的多件事被压成一个意图；一轮只分派一次 |
| 自然语言交接 | 子 Agent 返回自然语言，再由 Composer 合成，事实可能在转述中被改错 |
| 没有完成检查 | 执行一次就结束，不核对原始诉求是否都已办完 |
| 收益未被证明 | OrderWeave 的 single 模式“成本约低 30%，成功率略低”，但没有正式对照；它的提升主要来自上下文编译、回复守卫、请求清单、两阶段写入等工程护栏 |

TTWill 改为**任务驱动的多 Agent**：

| 维度 | EchoMind / OrderWeave | TTWill |
| --- | --- | --- |
| 拆分依据 | 通用角色 | 业务能力（订单服务、售后，第二阶段加导购） |
| 分派方式 | 每轮一个意图，一主一辅 | 协调者维护任务清单，按任务分派，可以同时派多个 |
| 返回内容 | 自然语言 + Composer 合成 | 结构化结果，协调者核对后生成回复 |
| 完成判断 | 执行一次即结束 | 对照任务清单检查，未完成则补做或追问 |
| 写权限 | 只有主角色能写 | 每种能力只能写自己范围内的数据；确认与核验由代码护栏负责 |

### 多 Agent 在 MVP 中是否必要

只看 MVP（订单 + 售后），各能力共用同一个用户、同几笔订单、同一份政策，多 Agent 的收益可能有限；放到整个项目看则有必要：导购、售后、商家侧在工具、数据、政策和上下文上差异明显。因此架构按多 Agent 设计，MVP 中的收益由实验回答（见 [03 实验设计.md](<03 实验设计.md>)）。

## 与 Claude Code 子 Agent 机制的对照

| 机制 | Claude Code | TTWill |
| --- | --- | --- |
| 定义子 Agent | 开发者预设：名称、描述、系统提示词、工具白名单、模型 | 相同，另加**输出格式**和读写权限标注 |
| 何时调用、调用几个 | 主 Agent 决定 | 协调者决定 |
| 任务说明 | 主 Agent 写 | 协调者写，并附上相关的任务状态和已确认事实 |
| 工具 | 由类型决定，调用时不能指定 | **相同** |
| 模型 | 类型定义默认，调用时可覆盖 | 相同（对应“多模型分层”） |
| 上下文 | 子 Agent 从空白上下文开始，只看到任务说明 | 相同 |
| 返回 | 一段自由文本 | **结构化结果** |
| 并行 | 一条消息里发出多个调用即并行 | 相同；同一订单的写任务除外（见代码护栏） |
| 层级 | 一般只有一层 | 相同 |

## 能力注册表

每种能力是注册表中的一条记录，新增场景只需加一条：

| 字段 | 说明 |
| --- | --- |
| `name` | 能力名称，如 `order_service` |
| `description` | 给协调者看：适合处理什么任务 |
| `prompt` / `skills` | 系统提示词；本能力可加载的 Skill 列表 |
| `tools` | 工具白名单，并标注读 / 写 |
| `output_schema` | 结构化返回约定；MVP 两种能力共用运行时代码的格式，不在每条能力记录里重复保存 |
| `model_tier` | 默认模型档位（如 flash / strong） |

### MVP 的能力划分

| 能力 | 职责与工具 | 说明 |
| --- | --- | --- |
| 协调者 | 身份验证、维护任务清单、分派任务、汇总后回复用户、转人工 | 身份验证是所有任务的前提，而且一次对话只服务一个用户 |
| 订单服务 | 查询；修改 / 取消待发货订单；修改用户地址 | 对应政策中待发货订单的部分 |
| 售后 | 已送达订单的退货、换货 | 对应政策中已送达订单的部分 |
| 导购（第二阶段） | 商品检索、比较、画像、下单 | 上下文与数据差异最大，最适合独立 |

### 子 Agent 结构化返回

以下按 D 组本体说明，实验消融的差异见 [03 实验设计.md](<03 实验设计.md#组件消融在-d-组内>)。下列对象是**运行时代码汇总的返回结果**，不是让模型完整填写的 JSON。模型提供 `missing` 与 `message_hint`；代码从网关调用记录填入动作、结果及待确认操作。任务 ID 和执行身份也由代码绑定。

```json
{
  "task_id": "t2",
  "status": "need_confirm",
  "actions": [{"tool": "exchange_delivered_order_items", "args": {}, "status": "prepared", "result": {"status": "prepared"}, "operation_id": "op_7f3a"}],
  "facts": [],
  "missing": [],
  "pending_confirmation": [{"operation_id": "op_7f3a", "action": "exchange_delivered_order_items", "args": {}, "preview": {}}],
  "message_hint": "给用户的关键信息要点（由协调者组织最终回复）"
}
```

| 内容 | 谁能写 |
| --- | --- |
| 任务新增 / 修改 / 撤销提议、`missing`、`message_hint` | 模型提出，代码校验后更新对应内容 |
| `task_id`、任务修订号 `revision`、身份、能力与实例 ID | 运行时代码维护，不能由模型伪造或覆盖 |
| `actions`、工具参数与执行结果、操作 ID、待确认详情 | 代码从网关与后端返回记录填入；D 组子 Agent 只能发起准备，重试可找回已提交状态，异常清理可记录拒绝结果，不能自行提交 |
| 业务事实 `facts` | 代码记录实际工具返回及其来源，模型不能把推测写成已验证事实 |
| 执行状态与失败原因 | 运行时根据实际执行记录更新，模型不能直接声明已执行 |
| 写任务的 `done` | 仅执行后核验代码可以设置；准备成功、模型声称成功或后端已提交都不等于核验完成 |

模型仍负责理解诉求、选择工具和判断自然语言条件；这里限制的是**可信状态的写入权**。确认判定器按下文约定使用规则或 LLM 判定用户原话，判定结果由护栏代码消费，不能通过普通任务更新接口伪造授权。

第 3 步的结束接口为 `finish(missing, message_hint)`，也接受同结构的 JSON 回复；多余字段和类型不符会被拒绝并反馈给模型，消耗循环预算。`finish` 必须单独调用。`pending_confirmation` 使用列表完整保留实际准备项，参数与预览来自后端；模型要点不作为确认凭据。模型对任务的增改撤提议由第 4 步协调者处理。

本次派工状态由代码计算：`need_confirm` 表示存在待确认准备项，`needs_verification` 表示重试找到已提交操作，`need_info` 表示仍缺信息，`ready` 仅表示只读派工拿到了业务查询结果，`failed` 表示超限或没有取得所需进展。它们是派工结果，不直接将写任务标为 `done`。

## “派几个实例”的含义

指**任务层面的并发**：同一种能力为不同子任务开多个独立上下文，用完即销毁。例如“这单耳机换黑色，那单键盘退货”，协调者同时派出两个售后实例，各看一笔订单。

这与 [项目优化清单](../../项目优化清单.md)（仓库外内部文档）第 03 项不同：03 的“多实例调度”是服务部署层面的负载均衡与故障切换，在 TTWill 中降为低优先级基础设施；03 的“多模型分层”由能力的 `model_tier` 吸收。

## 拆分原则

**看上下文和政策是否属于同一块，而不是看工具数量。** 值得拆分的情况：权限不同（只读 vs 写）、上下文不同（导购的候选商品 vs 售后的订单明细）、独立可并行、适合不同模型。工具多时在 Agent 内部解决（Skill 按需加载），不为此拆分。

## 协调者与任务状态

协调者是唯一面对用户的 Agent，维护一份结构化任务状态：

```json
{"session": {"session_id": "chat_1", "user_id": "..."},
 "tasks": [
  {"id": "t1", "revision": 1, "action": "exchange_delivered_order_items", "order_id": "W123", "status": "waiting_info", "missing": ["新颜色"], "capability": "after_sales"},
  {"id": "t2", "revision": 1, "action": "modify_pending_order_address", "order_id": "W456", "status": "pending_confirm", "capability": "order_service"},
  {"id": "t3", "revision": 1, "action": "return_delivered_order_items", "order_id": "W123", "status": "conditional", "condition": "t1 无法完成时执行", "capability": "after_sales"}
 ],
 "last_display": [], "history": [], "turn": 1}
```

上例省略了各任务的 `instruction`、`facts`、`actions`、`operation_ids`、`message_hint`、`reason` 等字段。第 4 步以 `ConversationState` 在内存中保存会话、任务和实际展示快照，不提供跨进程恢复；第 5 步再接入唯一的任务检查点。任务状态包括 `pending`、`conditional`、`running`、`waiting_info`、`pending_confirm`、`needs_verification`、`done`、`cancelled`、`failed`；子 Agent 的 `need_confirm` / `need_info` 是派工返回值，由协调代码转换为任务状态。

每轮流程：

```text
用户消息
  → 协调者提出任务新增 / 修改 / 撤销，代码应用更新；关联的尚未提交的旧操作先作废
  → 对最近一次回复展示过、且仍有效的操作判定确认；已确认的操作由护栏代码提交并核验
  → 对可推进的任务分派子 Agent（可并行）
  → 代码汇总网关记录与模型提供的信息缺口、回复要点，更新任务状态
  → 有待确认的写操作：向用户展示详情，暂停等待
  → 对照任务清单检查完成情况，生成回复
```

协调者通过工具（如 `update_tasks`）提出任务增、改、撤，代码只应用允许修改的字段；任务更新复用协调者已有调用。`condition` 保留自然语言，由协调者判断条件是否满足，不引入条件表达式解析器或依赖执行引擎。判断分支仍须遵守业务规则、确认与核验护栏。

第 4 步的具体接口是 `update_tasks`、`complete_plan`、`dispatch_tasks`、`reply`：先提出本轮全部新增、改口和撤销，调用 `complete_plan` 后代码才判定当前用户原话，随后允许分派和回复。协调者每次只调用一个工具，批量变更或分派放在该工具的列表参数中。任务变更整批校验后应用；任务 ID、修订号、执行状态、事实与操作引用不能出现在模型的更新字段中。能力及业务动作目录从入口注册表提供。

本步回复按实际任务状态和业务记录生成；待确认项展示完整办理参数及该动作相关预期结果，并保存实际展示原文。模型的 `message_hint` 保留为要点，无任务时可用于引导用户提供身份信息；它不能覆盖办理状态。只读任务也须取得对应动作和目标的查询事实才能完成。仍有可推进任务时，代码拒绝提前回复并让协调者继续决策。

条件备用任务已不再需要时，由协调者提出撤销，代码记录“条件分支不再需要”及具体原因，将其视为终止状态，不计为执行失败。例如换货已成功，备用退货任务应撤销，不继续停留在 `conditional`。条件尚未确定时保留任务，继续推进前置事项或等待用户。

订单写任务以**订单 × 动作类型**为粒度。同一订单同一类的商品修改或换货先汇总完整清单，再一次性准备；不拆成多个会消耗“一次修改机会”的操作。同一订单的不同动作逐个准备、逐个确认；先改地址、后改商品等动作顺序写进对应 Skill，由后端在提交时再校验业务规则。

### 确认与提交

子 Agent 用完即销毁，而用户的确认在下一轮才到，所以**提交执行由代码凭操作 ID 完成**。确认判定必要时调用独立 LLM，模型不持有本体的提交工具：

1. 子 Agent 调用写工具时，后端只做“准备”，返回操作 ID 和待确认详情；代码将网关记录填入结构化返回的 `pending_confirmation`；
2. 代码把操作引用写入任务状态，协调者向用户展示详情，并记录本次回复实际展示的操作 ID 与内容；
3. 用户下一条消息到达时，先应用涉及旧任务的修改或撤销，使关联的尚未提交的旧操作作废，再由确认判定器逐项判断仍有效且最近一次回复展示过的操作；
4. 判定为确认的操作，由护栏代码通过网关凭操作 ID 调用后端提交，再做执行后核验，结果写回任务状态；一次确认多个操作而部分失败时，按操作逐个汇报。

协调者和子 Agent 都没有“提交”工具，模型无法在没有用户确认的情况下触发写入。

> 实验对照：A / B 组和“D − 确认”消融组使用另一种工具包装，向模型开放“提交”工具，由模型在用户确认后自行调用，确认只靠政策文字约束。业务后端不变，变的只是谁有权提交。“D − 确认”中提交工具由协调者持有：子 Agent 准备后即销毁、看不到用户消息，只有协调者掌握任务状态中的操作 ID 并能看到用户原话。见 [03 实验设计.md](<03 实验设计.md>)。

**确认判定：规则 + LLM 判定**

| 步骤 | 做法 |
| --- | --- |
| 规则 | 最近一次回复只展示一个待确认操作，且用户明确同意（“好的”“确认”“可以”等）、不含修改内容时，可直接确认；拒绝也必须能明确对应到操作 |
| LLM 判定 | 规则判定不了时调用。单独一次调用，输入只有待确认操作的展示内容和用户原话，按操作 ID 输出“确认 / 拒绝 / 修改 / 无关”及依据；多操作时不能把无明确范围的短回复自动扩展为全部确认 |
| 判定失败 | LLM 调用失败或输出不合格 → 按未确认处理，不执行写入 |

- 带修改的确认（“可以，不过换成白色”）判为“修改”：原操作作废，按新要求重新准备；
- **只有最近一次助手回复实际展示的操作可以被确认**；有多个待确认操作时逐操作 ID 判定，“都可以”也只覆盖该次展示且仍有效的操作；
- 展示多个操作时，明确“全部确认”“都可以”才能整体确认；指名的确认只适用于对应操作。只有“好的”等范围不明的回复时继续追问，不提交范围未确定的操作；
- 判定器保留上一回复的完整展示范围；本轮修改或撤销其中一项，不会把原本多项的“好的”缩小解释为确认剩余一项。代码再核对会话、轮次、任务修订号及后端参数，只执行仍有效的判定项；
- 没有得到确认不等于操作或任务作废；任务保留，操作若未在最近一次回复中展示，必须重新展示才能再次确认。跨会话续办一律重新展示；
- 任务被修改或撤销时，相关尚未提交的旧操作作废，不能继续凭旧操作 ID 提交；已经提交的业务事实与操作记录保留；
- 后端操作的 TTL 仅作兜底，与对话授权分开：TTL 未到不代表用户已授权，已过期的操作即使得到确认也不能提交；
- 每次判定（规则命中项或 LLM 输出、最终结果）都写入轨迹的 `confirmation` span。

待提交操作被拒绝、因任务修改 / 撤销而作废、TTL 到期或确定无法继续执行时，清理旧操作并释放对应订单的占用；需要继续办理的任务重新准备、展示并等待确认。仅仅暂未确认不释放占用。提交结果未知时先对账，不把未知结果当作确定失败后继续执行下一项写操作。

### 代码护栏

| 护栏 | 作用 |
| --- | --- |
| 写操作两阶段：首次调用只生成待确认详情；用户在**后续消息**中明确确认后才由代码提交 | 防止未确认的写入 |
| 确认只来自真实用户消息的判定结果，并核对提交参数与展示内容一致 | 模型无法自行授权 |
| 执行后核验：提交后重新读取业务数据，核对结果与确认时展示的操作一致（订单状态、商品规格、金额等），一致才标记完成 | 防止“以为办成了” |
| 协调者循环：本轮仍有可推进的任务（已分派未返回、可执行未执行）时，不能直接生成回复结束本轮；只有所有任务均已完成、已撤销并记录原因、等待用户（待确认 / 缺信息）或已失败并说明原因时才能结束；不再需要的条件分支按撤销处理 | 防止工具没跑完就结束，也避免无须执行的备用分支无限挂起 |
| 同一订单的写任务串行锁从准备开始，持续到提交或操作被拒绝；等待确认期间继续占用。同单同类商品先汇总，同单不同动作逐个确认 | 避免并行冲突以及将“一次性修改”误拆成多个操作；旧操作因任务修改 / 撤销作废后释放占用 |
| 身份与归属：查找用户的工具成功返回唯一用户时，网关记录本会话的已验证身份，之后不能切换用户；验证前只开放查找用户的工具；后端拒绝操作不属于该用户的订单和地址 | 不依赖模型遵守身份规则 |
| 写操作去重、结果未知时不盲目重试 | 防止重复执行 |
| 子 Agent 工具循环步数、每轮分派轮数均有配置上限；超限时由代码将受影响的未完成任务标为 `failed` 并记录原因 | 防止无进展循环；协调者向用户解释或按政策转人工，轨迹记录 `guard` span |

第 4 步核验从网关重读订单或用户地址，逐动作比较确认预览中的状态、地址、商品规格和价格、支付与退款明细、退换货清单及差价等相关字段。核验结果保留预期值、实际值、检查字段和失败原因。当前不独立核验账户余额；后端事务测试另行验证余额变化。后端已提交但结果不一致时保留提交事实并标记失败，不重复写入。

## 工具与业务后端

### 两层结构

```text
子 Agent 看到的工具（Agent 层，TTWill 定义）
  名称、描述、参数结构、读 / 写标记、轨迹打点
        │
        ▼  工具网关：call(context, tool_name, args) -> result
           context 由代码构造：会话身份 + 能力 + 实例 ID
        │
业务后端（实现层，TTWill 自己实现）
  业务数据库 + 业务规则 + 写操作的准备 / 提交
```

- **工具注册一次，能力只引用名称**：能力注册表中的 `tools` 是工具名白名单；
- **工具网关**是 Agent 访问业务后端的唯一入口；MVP 中 `gateway/` 直接导入 `backend/`，`core/` 只持有网关实例，不导入 `backend/`；
- 与 MCP 的客户端 / 服务端分层同一思路。MVP 中后端在进程内直接调用，后续可做成 MCP 服务端。

不为后端另写一层 Protocol 或可替换后端框架。网关及后端测试使用 fixture 创建的小型 SQLite 库，直接验证真实的业务行为。

### 业务后端：自己实现，不调用 τ² 的工具代码

| 项 | 做法 |
| --- | --- |
| 数据 | 直接导入 τ²-bench 中文包**已编译好的中文数据库**（`data/tau2/multilingual/zh/regional/retail.json`：500 用户、1000 订单、50 种商品） |
| 数据库 | **SQLite**：单文件、无需服务、支持事务。每个评测任务的一次重复运行独立初始化业务库；该次运行中的多段聊天共用同一个库。通过 SQLAlchemy 访问，需要时可迁移到 PostgreSQL |
| 业务规则 | 自己实现订单与售后操作，MVP 语义与 τ² retail 政策一致（如只有待发货订单能取消），以便评测 |
| 写操作 | 通用的**准备 / 提交**接口：准备请求使用稳定关联标识，后端记录其与操作 ID 的关系；同一请求重复准备返回已有结果，不新建重复操作。凭操作 ID 提交时校验参数一致、未过期、未重复执行，并重新校验业务规则；提交与核销在同一事务中完成 |
| 身份 | 调用方带上已验证的用户身份，后端校验订单、地址、支付方式的归属 |
| 操作记录 | 待提交操作、提交结果、业务事件、去重记录保存在业务库中，是写入结果与恢复对账的权威依据；不存第二份 Agent 任务状态 |

准备请求的关联标识由代码按 **`task_id + revision + 动作类型`** 确定性生成；这里的 `task_id` 对应任务状态中的 `id`。任务 ID 与修订号在协调层正常节点边界形成可恢复的任务状态后，才用于派出子 Agent，不在工具循环内临时随机生成。同一请求跨实例重试或恢复重放时使用相同标识，不依赖实例 ID 或调用次数。任务请求内容修改时，由代码递增 `revision`；失效操作需要重新准备为新请求时也递增。普通状态更新、重试与恢复不递增修订号。

同一标识与相同参数返回已有操作，同一标识携带不同参数时拒绝。关联记录与准备操作一并保存，用于恢复时定位后端已生成、但尚未写入任务检查点的操作。这些是业务操作及去重记录，不另存一份任务清单。

为什么不直接用 τ² 的工具：

- τ² 的写工具调用即生效，无法在业务层插入“先准备、确认后提交”；
- **职责分开**：业务层只提供通用的准备 / 提交接口，不理解对话；“用户是否确认”由 Agent 层判定。业务后端因此可以独立成为购物平台，Agent 只是它的客户端；
- 这个后端就是自建购物平台的起点（见 [01 阶段规划与MVP.md](<01 阶段规划与MVP.md#自建平台计划>)）。

代价：需要实现 MVP 涉及的操作，并做一次与 τ² 的语义一致性校验。

### 接入 τ²-bench 评测

| 环节 | 做法 |
| --- | --- |
| Agent 接入 | 整个多 Agent 系统包装成一个 τ² Agent（`HalfDuplexAgent`），接官方用户模拟器 |
| 工具调用不进入 τ² 环境 | 我们的工具调用走自己的业务后端，τ² 只看到 Agent 与用户之间的文本消息 |
| 判分 | 自写评测入口，复用 τ² 的用户模拟器和判分组件，但**替换“预测侧”数据库**：用我们业务库的快照构造 τ² 环境（`get_environment(db=RetailDB(快照))`），并跳过它默认的轨迹重放；“参考侧”仍按官方方式加载原始数据库并执行参考动作。两边计算数据库哈希比对；自然语言断言照常基于对话文本判定 |
| 语义一致性校验 | 第 2 步先重放 `retail_50` 的官方中文参考动作，比较 τ² 官方工具与自建后端的数据库哈希；7 个写工具中未被这些题覆盖的操作补无模型单测。第 9 步转换其余 64 题后扩充参考动作校验 |
| τ² 协议相关的政策条款 | 政策中“一次只调用一个工具”“调用工具时不能同时回复用户”描述的是 τ² 自己的工具协议。我们的工具调用不经过 τ²，适配层每轮只向 τ² 返回一条文本回复，因此这两条不适用，不写进核心 |

**为什么要替换预测侧**：τ² 默认把轨迹中的工具调用在新环境上重放，得到预测侧数据库。我们的工具调用不在轨迹里，直接重放会得到未修改的初始库。

注意事项：

- 数据库哈希覆盖整个库，快照必须逐字段与 τ² 数据模型一致（状态字符串、支付记录、金额精度等），由一致性校验保证；
- 参考侧与我们的初始数据必须是同一份中文数据库；
- 任务的 `initial_state` 若带初始化动作（官方题均为空，自建跨会话任务可能用到），需同时作用到我们的业务库上。

OrderWeave 的 `evaluation/tau_eval_worker.py` 采用同样做法，可作实现参考。

## Skill 与政策

Skill 回答“按什么规则办”，工具（含检索）回答“根据什么事实、做什么动作”。

### 政策拆分

τ² retail 政策按动作分章节，按章节分到协调者和各能力：

| 内容 | 放在哪里 |
| --- | --- |
| 通用规则：身份验证、一次只服务一个用户、不编造信息、转人工条件、领域基础说明 | 协调者的固定提示词（常驻） |
| 取消、修改（地址 / 支付 / 商品）、修改用户地址 | 订单服务能力的 Skill |
| 退货、换货 | 售后能力的 Skill |

Skill 文件只**引用政策章节名**，不复制原文。加载器先按下表排除不适用的 τ² 工具协议条款，再分配剩余章节；没有被任何 Skill 引用的适用章节常驻。**保留下来的政策原文不改写**，动作顺序等本项目操作要点单独写在 Skill 中。

| 排除条款 | 原因 |
| --- | --- |
| 一次只调用一个工具 | 描述 τ² 自身工具协议；本项目内部由网关执行，可并行处理不同订单 |
| 调用工具时不能同时回复用户 | 内部工具调用不进入 τ² 轨迹，适配层每轮仅返回一条文本回复 |

排除清单用于加载器显式过滤，不通过改写原始政策文件实现。

当前固定中文包中的政策正文仍为英文，按原文加载；中文只用于 Skill 操作要点。章节提取与两项排除文本位于 `bench/policy.py`，通用加载器接收章节字典和排除清单。默认用户地址没有独立专章，相关 Skill 的章节引用为空，适用规则保留在常驻政策中。

### 加载机制

1. 子 Agent 的提示词只列出**本能力范围内**的 Skill 目录（名称 + 一句话描述）；
2. 子 Agent 调用 `load_skill(name)` 取回正文：对应政策章节原文 + 操作要点；
3. 每个 Skill 声明关联的写工具；**当前实例加载对应 Skill 前，关联的写工具被拒绝调用**，保证执行前读过该动作的政策；
4. Skill 只提供文本，不授权写入；确认仍由护栏判定。

协调者派出子 Agent 时，代码构造“会话身份 + 能力 + 实例 ID”的调用上下文；网关据此校验能力白名单。Skill 加载记录按**实例**保存，实例销毁时清除，不因同一会话中的其他实例读过政策而解锁。子 Agent 不持久化，后续分派的新实例重新按需加载自己的 Skill。

Skill 使用 TOML 前导元数据，两个 `+++` 之间由标准库解析。文件格式（示意）：

```text
skills/return_delivered_order/SKILL.md
+++
name = "return_delivered_order"
description = "已送达订单的退货（商品清单、退款去向限制）"
capability = "after_sales"
tools = ["return_delivered_order_items"]
policy_sections = ["Return delivered order"]
+++
1. 先查订单，确认状态为 delivered……
2. 收集该订单所有要退的商品……
3. 退款去向只能是原支付方式或已有礼品卡……
```

### 与多 Agent 的结合

- 每个子 Agent 只看到自己能力的 Skill 目录，上下文比单 Agent 下的完整目录更小；
- 能力注册表中的 `skills` 字段即该能力可加载的 Skill 列表；
- 单 Agent 组（A / C）看到全部 Skill 目录，加载机制相同。

### MVP 中的定位

τ² 政策约 140 行，MVP 中按需加载的收益有限；第二阶段加入导购政策后政策量会明显增加。可选小消融：整份政策常驻 vs 按需加载。

机制参照 Claude Code 的 Skill；“加载后才解锁写工具”是本项目的约束。OrderWeave 的 `core/retail_skills.py` 有同类实现，可作实现对照。

## 检索（RAG）

MVP 不做：业务数据全是结构化的，查询走业务工具即可；政策由 Skill 管理。

### 第二阶段：服务主线业务

RAG 以**子 Agent 的工具**形式出现，挂在工具网关后面，与业务工具同样接入：

| 位置 | 检索对象 | 做法 |
| --- | --- | --- |
| 导购能力的商品检索工具 | 商品描述、适用场景、评价摘要 | LLM 把需求解析为结构化过滤条件 + 检索词；关键词（BM25）+ 向量混合召回，RRF 融合；结构化过滤；个性化排序；专用重排模型精排 |
| 政策 / FAQ 检索工具 | 导购政策、退换货 FAQ、商品使用说明 | 按章节结构分块，保留章节路径；回答引用来源 |
| 长期记忆检索 | 用户画像、历史服务摘要 | 按当前需求取出相关偏好与历史 |

导购检索的整体路线见 [00 项目定位.md](<00 项目定位.md#导购技术路线第二阶段>)。

### 检索技术栈

BM25 + 向量 + RRF + 交叉编码器重排，是 2026 年较公认的混合检索默认方案（[ai-cookbook](https://github.com/daveebbelaar/ai-cookbook/blob/main/knowledge/hybrid-retrieval/README.md) 称之为“在公开基准上胜出的朴素混合基线”）。

| 环节 | 主流选择 | 为什么 | 其他选项 |
| --- | --- | --- | --- |
| 稀疏召回 | BM25 | 精确匹配型号、ID、品牌、罕见词，是向量的弱项 | SPLADE（学习型稀疏向量，有同义扩展能力，需要跑模型） |
| 稠密召回 | embedding 模型 + 向量索引 | 理解同义改写和概念性查询 | 中文常用 BGE-M3、Qwen3-Embedding；BGE-M3 可同时输出稠密与稀疏向量 |
| 融合 | RRF | 按排名融合，不需要对齐两路分数尺度 | 加权分数融合（EchoMind Java 版的做法，需要归一化，难调） |
| 重排 | 交叉编码器 | 查询与文档一起打分，比双塔召回更准；只处理前几十个候选 | 聊天模型打分（贵且不稳定）；专用重排模型如 bge-reranker、Qwen3-Reranker |
| 存储 | 小规模：SQLite FTS5（BM25）+ 向量库 | 无需额外服务 | Elasticsearch（原生支持 BM25、HNSW、RRF）；pgvector |

商品检索在此之外还需要：LLM 把需求解析为**结构化过滤条件**（self-query，参考 [arXiv 2601.16492](https://arxiv.org/pdf/2601.16492)）、画像参与排序。专门训练双塔模型（如 [Flipkart 的工作](https://arxiv.org/pdf/2606.01504)）适合更大规模，本项目暂不需要。

具体的 embedding 与重排模型，在第二阶段用实际商品数据对比后确定。

### 提高召回的方法

两类方法互补：

| 类别 | 做法 | 例子 | 何时计算 |
| --- | --- | --- | --- |
| 文档端（离线） | 让文档更容易被找到 | 伪查询（为每个商品生成“用户可能怎么问”）、补充属性与标签、doc2query | 建索引时一次，查询时无额外开销 |
| 查询端（在线） | 让查询更好地匹配 | 查询改写、多查询扩展、HyDE、查询分解、根据召回结果补检 | 每次查询 |

查询端的常见做法：

| 方法 | 做法 | 优点 | 问题 |
| --- | --- | --- | --- |
| 多查询改写（EchoMind） | LLM 把原问题改写成多个角度的子查询，并行检索后合并 | 简单，覆盖不同侧面 | 改写可能漂移、丢掉约束（如“300 元以内”）；每次多一次 LLM 调用 |
| HyDE | LLM 先写一段假想答案，用它的向量检索 | 查询与文档表述风格更接近 | 假想答案可能编造事实把召回带偏；对商品检索帮助有限 |
| 查询分解 | 复合问题拆成子问题分别检索 | 适合“既要……又要……” | 需要判断该不该拆 |
| 结构化解析（self-query） | LLM 把需求解析为过滤条件 + 检索词 | 硬约束不会因改写丢失 | 依赖属性体系完整 |
| 规则覆盖检查 + 补检（OrderWeave） | 正则从问题中抽取需求点，检查结果是否覆盖，缺失的补检一次 | 可解释、确定、无额外 LLM 调用 | 见下文 |
| Agent 迭代检索（agentic RAG） | 检索作为工具，模型看结果不满意就换查询再检索 | 灵活，天然适合 Agent 架构 | 需要控制轮数与成本 |

**对 OrderWeave 覆盖检查的评价**：思路可取，做法不可迁移。

- 要解决的问题真实存在：复合问题召回的结果可能只覆盖部分需求；“检查覆盖、缺了再补”的思路与 Self-RAG、CRAG 等工作一致；
- 但需求点是 12 条手写正则（如 `退货条件|资格|能退`、`蓝牙配对步骤`），只对它自编的耳机排障资料有效，换领域或换说法就失效，每加一类需求都要人工补规则，与 EchoMind 关键词匹配 Skill 是同类问题；
- 更好的做法：需求点由模型提取（最好复用已有的模型调用），覆盖判断用结构化条件核对或 embedding 相似度，或由 Agent 看结果决定是否再查。

### TTWill 的召回方案

采用**结构化解析 + Agent 迭代检索 + 离线伪查询**，不单设查询改写环节：

| # | 做法 | 说明 |
| --- | --- | --- |
| 1 | 结构化解析作为检索工具的入参 | 导购子 Agent 调用 `search_products(filters, query_text, ...)` 时自己填写过滤条件与检索词；解析发生在本来就要做的工具调用里，**不额外增加 LLM 调用**；硬约束由过滤条件保证，不会在改写中丢失 |
| 2 | 多角度检索由 Agent 决定 | 子 Agent 可以在一轮里用不同检索词多次检索（如“轻便耳机”“头戴式 降噪”），相当于把多查询改写交给 Agent 按需进行，而不是固定每次改写 3 个 |
| 3 | 覆盖检查基于结构化需求 | 用户需求解析成结构化条件后，代码逐条核对检索结果是否满足（价格、类型等属性），条件来自结构化需求而不是正则；不满足时由 Agent 补检或向用户说明缺口 |
| 4 | 离线伪查询 | 建商品索引时由 LLM 为每个商品生成几条用户式问法，一起索引 |
| 5 | 政策 / FAQ 检索 | 保留多查询改写的思路并加约束检查；体量小，优先级低 |

每种做法都可以单独评测：伪查询开 / 关、Agent 迭代检索开 / 关，作为第二阶段检索评测的消融项。

### 配套检索评测

第二阶段同时建立检索评测：召回率、约束满足率、排序指标，以及检索证据是否支持最终回答。[项目优化清单](../../项目优化清单.md)（仓库外内部文档）第 02 项（分块、混合召回、重排、检索题集）在这里落地。

| 来源 | 借鉴 | 不沿用 |
| --- | --- | --- |
| OrderWeave | BM25 + 向量 + RRF 的混合检索、专用重排模型（Qwen3-Reranker）；“检查覆盖、缺了再补”的思路 | 只用于一个边缘排障场景、评测时默认关闭；靠手写正则做证据覆盖检查（改为基于结构化需求核对） |

## 记忆与上下文

### 分层

多 Agent 本身提供了一部分上下文隔离：子 Agent 从空白上下文开始，只拿到任务说明，用完即销毁。会持续增长的主要是**协调者的上下文**（长对话、跨会话续办、第二阶段导购的大量候选商品）。

| 层 | 内容 | 存储 | 解决的问题 | 阶段 |
| --- | --- | --- | --- | --- |
| 1. 对话档案 | 完整消息与事件，只追加 | 由 `persistence/` 的小型存取模块保存 | 回溯、审计、重新生成摘要 | MVP |
| 2. 任务状态 | 任务清单、已确认事实、待确认操作引用 | **仅 LangGraph 检查点**；不另存一份独立的任务状态 | “办到哪一步了”，跨会话续办的核心 | MVP |
| 3. 上下文编译 | 每轮从 1、2 组装协调者的模型输入，带预算与压缩 | 每轮组装；摘要由 `persistence/` 保存 | 长对话不超上下文、成本可控 | MVP |
| 4. 长期记忆 | 用户画像（结构化偏好）、历史服务摘要 | 业务库 + 检索 | 跨会话“认识这个用户” | 第二阶段（见 [04 用户画像约定.md](<04 用户画像约定.md>)） |

**核心原则：按字段写入权限维护的任务状态是可信记忆，历史对话只供参考。** 任务状态以 LangGraph 检查点为唯一持久化来源，业务写入结果以后端操作记录为准。轨迹中的状态快照只供观察与审计，不作为另一套恢复来源。压缩可以从模型上下文中移除旧对话，但保留完整对话档案。

### 上下文编译

**每轮组装上下文是纯代码操作，不调用模型**：按规则从对话档案和任务状态中挑选、拼接内容。

布局按“稳定在前、可变在后”，以利于模型服务的前缀缓存：

```text
系统提示 + 政策 + 工具定义        ← 稳定，几乎每轮相同
历史消息（含已压缩部分）          ← 只追加
本轮任务状态快照 + 用户消息       ← 每轮变化
```

超出预算时分级处理：

| 级别 | 做法 | 是否调用模型 |
| --- | --- | --- |
| 1. 旧工具结果引用化 | 较早轮次的工具结果替换为引用（如“订单 W123 详情，需要时重新查询”）；业务数据随时可查，不丢信息 | 否 |
| 2. 早期轮次摘要 | 仍超预算时，把较早轮次写成摘要，标注“仅供参考，不构成用户确认” | **是，仅在触发时一次** |
| 3. 持久化 | 压缩结果通过 `persistence/` 保存，之后各轮直接复用，不重复压缩 | 否 |

因此正常情况下每轮**没有额外的模型调用**。摘要只在对话长到超过预算时触发一次，之后复用，直到再次超预算。摘要可以使用便宜的模型档位。

子 Agent 不做压缩：它的输入由协调者写的任务说明加相关事实组成，本身就是按需裁剪。

### 跨会话续办

同一业务任务可以跨多个聊天会话。续办时先重新验证身份，再加载该用户的 LangGraph 任务检查点、最近几轮对话与早期摘要；不能直接沿用上段聊天的 `verified=true`。

恢复后通过网关查询后端操作记录并对账：已经提交、但检查点还停留在待提交状态的操作，按后端记录更新为已提交，不重复提交；如果尚未完成结果核验，继续核验，通过后才把写任务标为 `done`。仍可办理的待确认操作一律重新展示，旧聊天中的展示或同意不自动授权新一轮提交；任务已修改 / 撤销或操作过期时，按“确认与提交”的规则处理。

同时覆盖**准备成功但操作 ID 尚未写入检查点**的中断窗口：恢复时从任务状态取得任务 ID、修订号与动作类型，按相同规则重新生成关联标识，再通过该标识及业务归属找回后端操作，补齐操作 ID 引用。同一请求所在节点重放时仍使用相同标识，不产生第二个操作。沿用 [LangGraph 在 super-step 边界保存完整图状态检查点的机制](https://docs.langchain.com/oss/python/langgraph/checkpointers)，不要求在子 Agent 的工具循环内、每次准备调用前单独保存检查点，也不为此把每次准备拆成图节点。

已失效或不再需要的待提交操作按既定规则清理并释放订单占用。找回操作不等于取得确认，仍须重新展示后才能提交。第 2 步验证确定性标识与准备幂等，第 5 步用断点测试验证引用恢复或清理，不能留下无法定位的待确认操作和占用。

每个评测任务的一次重复运行使用独立的业务库及检查点范围；该次运行中的多段聊天共享它们。不同题目或不同重复运行互不共享业务进度。

τ² 官方题平均约 4.8 步，基本不会触发压缩；压缩的价值主要体现在困难任务和第二阶段导购中。MVP 中压缩做到可用即可，阈值在评测阶段调整。参考：OrderWeave 的上下文编译、Pico 的分段预算与压缩顺序。

## 可暂停、可恢复的运行时

等待用户确认（写操作展示详情后暂停）和跨会话继续（从持久化状态恢复）用同一套机制：协调层使用 LangGraph 的检查点与中断 / 恢复；子 Agent 内部的工具循环自行实现。工具调用在进程内同步完成，不需要为等待工具结果而暂停。

`core/` 直接使用 LangGraph 的 checkpointer；`persistence/` 只提供检查点存储的初始化及对话、摘要所需的小型存取模块，不再包装通用持久化 Protocol。子 Agent 用完即销毁，不保存或恢复其实例上下文及 Skill 加载记录。

运行配置提供两个循环上限：**每个子 Agent 工具循环的步数**、**每轮用户消息最多进行的分派轮数**。触及上限后若仍需继续执行，代码将受影响的未完成任务标记为 `failed`、记录具体原因和 `guard` span，由协调者说明情况或按政策转人工；已有的确定结果保留，写入结果未知的操作先对账。上限数值在配置中设置，不硬编码在循环里。

第 3 步接入 `[agent].max_steps`，开发默认值为 12：每个工具调用计一步，没有工具调用的回复也计一步；同轮多个调用逐个计数，不能批量绕过上限。正常结束保留准备项；超限、取消或异常退出时作废本实例尚未提交的准备项，并清除 Skill 加载记录。

第 4 步接入 `[agent].max_rounds`，开发默认值为 8，按每条用户消息的协调决策计数：身份查询、更新任务、结束计划、分派、回复及无效输出各计一轮。每轮最多发起一批分派，因此分派轮数不会超过该值，连续无效决策也会终止。达到上限时，仍须推进的任务失败；已等待用户确认或补充信息的结果保留，回复始终说明超限原因。取消和 I/O 失败时，收拢并行实例、保留实际操作引用并清理未提交准备项；清理仍失败时保留引用供后续对账。

### 职责与依赖边界

| 位置 | 负责什么 | 边界 |
| --- | --- | --- |
| `cli.py` / `bootstrap.py` | 接收输入、选择配置、组装具体实现 | 不写业务规则；CLI 与后续评测入口复用同一本体 |
| `core/` | 任务推进、确认与核验策略、通用执行循环、上下文与运行时 | 不导入具体 `backend/`、`bench/`、`baselines/`；具体能力由入口注册，不在核心中按名称硬编码 |
| `agents/` | 定义各业务能力及其模型可见内容 | 不为每种能力复制工具循环；不直接读写数据库 |
| `gateway/` | 定义业务工具、校验调用上下文，直接导入并调用 `backend/` | `core/` 持有网关实例；Agent 的业务访问都走这里，工具只注册一次 |
| `backend/` | 维护业务事实与事务，执行准备 / 提交 | 不理解用户对话，不调用 Agent，不导入 τ² 类型；提供本项目的导入 / 导出接口供适配层使用 |
| `persistence/` | 对话档案、摘要的小型存取模块和 checkpointer 初始化 | 核心直接使用 LangGraph checkpointer；不另包装存取接口，不维护第二份任务状态 |
| `llm/` / `tracing/` | 模型调用与统一记录 | `llm/` 向 `tracing/` 写记录，轨迹层不反向调用模型；τ² 内部调用仍按工程约定接回调 |
| `bench/` | 理解 τ² 的数据、类型、协议与判分 | 转换后调用本体或后端；核心与业务后端不能反向依赖它 |
| `baselines/` | 实现实验中的替代编排方式 | D 组直接使用本体；共用后端、工具与基础设施，不复制业务规则 |

MVP 不为 `backend/` 或 `persistence/` 各建一层 Protocol，也不建立通用 `common/`、`utils/` 或依赖注入框架。`bootstrap.py` 只负责创建具体对象与启动；测试使用假模型及 fixture 创建的小型 SQLite 库。

`backend/` 维护业务记录，`persistence/` 维护对话档案、摘要并接入 LangGraph 检查点。任务状态只在检查点中持久化；后端保存独立的业务操作记录，恢复时按“跨会话续办”对账。这是代码职责的划分，不要求增加独立存储服务。

### 配置、资源与运行产物

- MVP 只有一份配置时使用根目录 `config.toml`，保存模型档位、两个循环上限等非敏感参数；密钥只来自 `.env`。接入 A / B / C / D 等实验、确实需要每组独立文件时再引入 `configs/`，不为单份配置单设目录或保留两份相同的默认值。
- `skills/` 保存本项目编写的动作说明；引用的政策原文由固定版本的数据输入提供。`bench/` 负责 τ² 来源的提取与转换，核心加载器只读取普通文本和章节索引。
- 启动入口统一解析配置、Skill 和数据路径，再传给组件；包内不依赖调用者当前工作目录去拼接 `../skills` 等路径。
- `data/` 保存输入及来源信息；每个评测任务的一次重复运行从种子初始化可变数据库，放入 `runs/<run_id>/` 下各自的样本目录，不改原始数据或种子。同一跨会话任务的多段聊天共用该库，按工程约定记录样本与会话归属。
- 文档、自有配置、Skill、自建题与小型测试数据纳入版本管理；外部数据是否随仓库分发按来源要求决定，并保留获取方式与校验值。可再生成的大文件、运行数据库、轨迹和模型原始记录不提交，初始化时同步补齐 `.gitignore`。
- τ² 的安装与测试依赖单独分组；普通安装、假模型测试和本体对话不要求安装 τ²。源码中 τ² 专属实现只放 `src/ttwill/bench/`，对应测试放 `tests/bench/`。

| 7～10 | 扩充 `bench/` 的评测接入与任务转换，加入 `baselines/`、任务清单及实验报告 |

每一步同步添加必要测试，`tests/` 不等到第 6 步才建立。第 2 步业务库已经保存待提交操作、业务事件与去重记录，第 5 步才补充完整的 Agent 状态恢复。

### 后续扩展

MVP 后再增加 `src/ttwill/api/`（FastAPI 入口）和根目录 `frontend/`（独立前端）；它们复用本体，不承载业务规则。第二阶段按实际需要增加导购能力、检索与画像实现，仍经工具网关访问业务数据。本轮不预建这些目录，也不决定前端或检索的具体技术栈。
